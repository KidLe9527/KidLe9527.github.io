## 1. 存储引擎

* 从上至下分为连接层，服务层，引擎层，存储层
* 不同的存储引擎有不同的功能，数据库中的索引是在存储引擎层实现的 ---> 不同的存储引擎的索引结构是不同的
* 存储引擎就是存储数据、建立索引，更新/查询数据等技术的实现方式
* 存储引擎是基于表的，而不是基于库的，所以存储引擎也可被称为表类型

### `InnoDB`

* 特点：
  * DML操作遵循ACID模型，支持**事务**；（DML-->数据的增删改，ACID ---> 事务的原子性、一致性、隔离性、持久性）
  * **行级锁**，提高并发访问性能；
  * 支持**外键**FOREIGN KEY约束，保证数据的完整性和正确性
* 文件：
  * xxx.ibd：xxx代表的是表名，innoDB引擎的每张表都会对应这样一个**表空间文件**存储该表的表结构（frm-早期的 、sdi-新版的）、数据和索引。（一个文件存储表结构、数据和索引）

### `MyISAM`

​	早期的MYSQL默认存储引擎。

* 特点：
  * 特点
    * 不支持事务，不支持外键
    * 支持表锁，不支持行锁
    * 访问速度快
* 文件：
  * xxx.sdi：存储表结构信息
  * xxx.MYD: 存储数据
  * xxx.MYI: 存储索引

### `Memory`

* 注意！Memory引擎的表结构**数据是存储在内存中的**，因此会受到硬件问题、或者断电问题的影响，只能作为临时表或缓存使用！
* 特点：
  * 数据存放在内存 ------> 访问速度快
  * 支持hash索引（默认）
* 文件：
  * xxx.sdi：存储表结构信息

### 三种存储引擎的区别

| 对比维度            | InnoDB                                                       | MyISAM                                                       | Memory（Heap）                                               |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **事务支持**        | 支持 ACID 特性（原子性、一致性、隔离性、持久性），支持事务提交 / 回滚 | 不支持事务，操作是 “原子性” 的（要么全成，要么全失败后无回滚） | 不支持事务，数据仅存于内存，断电 / 重启后丢失                |
| **行级锁 / 表级锁** | 支持**行级锁**（仅锁定修改的行，并发性能高），也支持表级锁   | 仅支持**表级锁**（修改时锁定整张表，并发写性能差）           | 仅支持**表级锁**，并发写性能受限                             |
| **外键约束**        | 支持外键（Foreign Key），保证数据完整性                      | 不支持外键                                                   | 不支持外键                                                   |
| **数据持久化**      | 支持（数据存储在磁盘，断电后不丢失）                         | 支持（数据存储在磁盘，断电后不丢失）                         | 不支持（数据仅存于内存，重启 MySQL 后清空）                  |
| **索引类型支持**    | 支持 B + 树索引（主键索引为聚簇索引，普通索引为辅助索引）、全文索引（MySQL 5.6+）、哈希索引（自适应） | 支持 B + 树索引、全文索引（早期 MySQL 默认支持），无聚簇索引 | **支持哈希索引（默认）**、B + 树索引（需手动指定）           |
| **聚簇索引**        | 有（主键索引即聚簇索引，数据与索引存储在一起）               | 无（索引与数据分离，索引仅存指针）                           | 无（数据存于内存，索引仅存内存地址）                         |
| **崩溃恢复**        | 支持（通过 redo log 和 undo log 实现崩溃后数据恢复，保证一致性） | 不支持（崩溃后可能出现数据碎片，需通过`myisamchk`修复）      | 无需恢复（数据已丢失，重启后自动重建空表）                   |
| **存储文件**        | 表结构（.frm）、数据 + 索引（.ibd，MySQL 5.7 + 默认独立表空间） | 表结构（.frm）、数据（.MYD）、索引（.MYI）                   | 仅表结构（.frm，数据存于内存，无磁盘文件）                   |
| **适用场景**        | 高并发写业务（如电商订单、金融交易）、需事务 / 外键的场景    | 只读 / 低频写业务（如博客文章、报表统计）、需全文索引的历史数据 | 临时数据存储（如临时计算结果）、高频访问的缓存表（需手动维护数据） |
| **内存占用**        | 较高（需缓存索引和数据，依赖 buffer pool）                   | 较低（仅缓存索引，依赖 key buffer）                          | 极高（所有数据存于内存，表大小受内存限制）                   |
| **表大小限制**      | 受操作系统文件大小限制（一般支持 TB 级）                     | 受操作系统文件大小限制（一般支持 GB 级，低于 InnoDB）        | 受内存大小限制（默认最大 64MB，可通过`max_heap_table_size`调整） |
| **是否支持 MVCC**   | 支持（多版本并发控制，读不加锁，提升并发读性能）             | 不支持（读操作会阻塞写，写操作会阻塞读）                     | 不支持（读 / 写互斥）                                        |

* 总结：`Innodb`支持事务、外键和行级锁，`MyISAM`都不支持

### 存储引擎的选择

* InnoDB: 是Mysql的默认存储引擎，支持事务、外键。如果应用对事务的完整性有比较高的要求，在并发条件下要求数据的一致性，数据操作除了插入和查询之外，还包含很多的更新、删除操作，那么InnoDB存储引擎是比较合适的选择。

* MyISAM ： 如果应用是以读操作和插入操作为主，只有很少的更新和删除操作，并且对事务的完整性、并发性要求不是很高，那么选择这个存储引擎是非常合适的。（被`mongodb`取代）

* MEMORY：将所有数据保存在内存中，访问速度快，通常用于临时表及缓存。MEMORY的缺陷就是对表的大小有限制，太大的表无法缓存在内存中，而且无法保障数据的安全性。（被`redis`取代）

## 💻InnoDB存储引擎

### InnoDB的逻辑存储结构

* **表空间**：表空间是InnoDB存储引擎逻辑结构的最高层， 如果用户启用了参数 innodb_file_per_table(在8.0版本中默认开启) ，则每张表都会有一个表空间（xxx.ibd），一个mysql实例可以对应多个表空间，用于存储记录、索引等数据。

* **段**：段，分为数据段（Leaf node segment）、索引段（Non-leaf node segment）、回滚段（Rollback segment），InnoDB是索引组织表，数据段就是B+树的叶子节点， 索引段即为B+树的非叶子节点。段用来管理多个Extent（区）。

* **区**：区，表空间的单元结构，每个区的大小为1M。 默认情况下， InnoDB存储引擎页大小为16K， 即一个区中一共有64个连续页。

* **页**：页，是InnoDB 存储引擎磁盘管理的最小单元，每个页的大小默认为 16KB。为了保证页的连续性，InnoDB 存储引擎每次从磁盘申请 4-5 个区。

* **行**：行，InnoDB 存储引擎数据是按行进行存放的。在行中，默认有两个隐藏字段：

  * Trx_id：每次对某条记录进行改动时，都会把对应的事务id赋值给trx_id隐藏列。

  * Roll_pointer：每次对某条引记录进行改动时，都会把旧的版本写入到undo日志中，然后这个隐藏列就相当于一个指针，可以通过它来找到该记录修改前的信息。

### 架构

​	MySQL5.5 版本开始，默认使用InnoDB存储引擎，它擅长事务处理，具有崩溃恢复特性，在日常开发中使用非常广泛。

#### **内存结构**

* Buffer Pool，缓冲池
* Change Buffer，更改缓冲区，针对非唯一二级索引
* Adaptive Hash Index，自适应hash索引，用于优化对Buffer Pool数据的查询。自适应哈希索引，**无需人工干预**，是系统根据情况自动完成。
* Log Buffer，日志缓冲区，redo log， undo log，占据大部分内存80%～提高mysql的执行效率

#### **磁盘结构**

* System Tablespace，系统表空间。系统表空间是更改缓冲区的存储区域。

* File-Per-Table Tablespaces，每个表的独立表空间，包含单个InnoDB表的数据和索引 ，并存储在文件系统上的单个数据文件中。

* General Tablespaces，通用表空间，手动创建

  * 创建语法：`create tablespace ts_name add datafile 'file_name' engine = engine_name;`
  * 建表时指定表空间：`create table xxx  tablespace ts_name;` 

* Undo Tablespaces，撤销表空间，MySQL实例在初始化时会自动创建两个默认的undo表空间（初始大小16M），用于存储

  undo log日志。

* Temporary Tablespaces，临时表空间

* Doublewrite Buffer Files，双写缓冲区，innoDB引擎将数据页从Buffer Pool刷新到磁盘前，先将数据页写入双写缓冲区文件

  中，便于系统异常时恢复数据。

* Redo Log，重做日志，是用来实现事务的持久性。

#### 后台线程

* 分类：分为4类，分别是：Master Thread 、IO Thread、Purge Thread、Page Cleaner Thread。
  * 作用：**将innodb存储引擎的缓冲池当中的数据在合适的时机刷新到磁盘文件中**
  * Master Thread
    * 核心后台线程，负责调度其他线程，还负责将缓冲池中的数据异步刷新到磁盘中, 保持数据的一致性，还包括脏页的刷新、合并插入缓存、undo页的回收 。
  * IO Thread
    * 在InnoDB存储引擎中大量使用了AIO（异步非阻塞io）来处理IO请求, 这样可以极大地提高数据库的性能，而IOThread主要负责这些IO请求的回调。
  * Purge Thread
    * 主要用于回收事务已经提交了的undo log，在事务提交之后，undo log可能不用了，就用它来回收。
  * Page Cleaner Thread。
    * 协助 Master Thread 刷新脏页到磁盘的线程，它可以减轻 Master Thread 的工作压力，减少阻塞。

### 事务原理🌟

​	事务 是一组操作的集合，它是一个不可分割的工作单位，事务会把所有的操作作为一个整体一起向系统提交或撤销操作请求，即这些操作要么同时成功，要么同时失败。

#### 特性

* 原子性（Atomicity）：事务是不可分割的最小操作单元，要么全部成功，要么全部失败。---> undo log

* 一致性（Consistency）：事务完成时，必须使所有的数据都保持一致状态。约束也要保证一致性 ---> undo log + redo log

* 隔离性（Isolation）：数据库系统提供的隔离机制，保证事务在不受外部并发操作影响的独立环境下运行。 --> 锁 + MVCC

* 持久性（Durability）：事务一旦提交或回滚，它对数据库中的数据的改变就是永久的。---> redo log

#### InnoDB引擎如何保证事务的四大特性

​	对于这四大特性，实际上分为两个部分。 其中的原子性、一致性、持久性，实际上是由InnoDB中的两份日志来保证的，一份是redo log日志，一份是undo log日志。 而隔离性是通过数据库的锁，加上MVCC来保证的。

##### `redo log`

* **重做日志**，记录的是事务提交时数据页的物理修改（物理日志，记录修改前的数据），是用来实现事务的持久性。
* 该日志文件由两部分组成：重做日志缓冲（redo log buffer）以及重做日志文件（redo logfile）,前者是在内存中，后者在磁盘中。当事务提交之后会把所有修改信息都存到该日志文件中, **用于在刷新脏页到磁盘,发生错误时, 进行数据恢复使用。**

##### `undo log`

* **回滚日志**，用于记录数据被修改前的信息 , 作用包含两个 : **提供回滚(保证事务的原子性) 和MVCC(多版本并发控制) 。**
* undo log和redo log记录物理日志不一样，它是逻辑日志（记录修改前的每一步执行的是什么操作）。可以认为当delete一条记录时，undolog中会记录一条对应的insert记录，反之亦然，当update一条记录时，它记录一条对应相反的update记录。当执行rollback时，就可以从undo log中的逻辑记录读取到相应的内容并进行回滚。
* Undo log销毁：undo log在事务执行时产生，事务提交时，并不会立即删除undo log，因为这些日志可能还用于MVCC。
* Undo log存储：undo log采用段的方式进行管理和记录，存放在前面介绍的 rollback segment回滚段中，内部包含1024个undo log segment。

##### `MVCC`多版本并发控制

###### 当前读

* 读取的是记录的**最新版本**，读取时还要保证其他并发事务不能修改当前记录，会对读取的记录进行加锁。
* 对于我们日常的操作，如：select ... lock in share mode(共享锁)，select ...for update、update、insert、delete(排他锁)都是一种当前读。
* 对于RR默认隔离级别，如果在一个事务中使用**当前读**读取另一个事务已经提交的改变的数据，那么当前读取的数据就是最新更改后的数据，而不是快照数据（原来的数据）

###### 快照读

* 简单的select（不加锁）就是快照读，快照读，读取的是记录数据的可见版本，有可能是历史数据，不加锁，是非阻塞读。

  * Read Committed：每次select，都生成一个快照读。

  * Repeatable Read：开启事务后第一个select语句才是快照读的地方。后续查询都是针对第一次select快照数据的查询

  * Serializable：快照读会退化为当前读。串行化

###### MVCC

* 全称 Multi-Version Concurrency Control，多版本并发控制。

* 指维护一个数据的多个版本，使得读写操作没有冲突，快照读为MySQL实现MVCC提供了一个非阻塞读功能。

* MVCC的具体实现，还需要依赖于数据库记录中的三个隐式字段、undo log日志、readView。

  * 隐藏字段

  | 隐藏字段    | 含义                                                         |
  | ----------- | ------------------------------------------------------------ |
  | DB_TRX_ID   | **最近修改事务 ID**，记录插入该记录或最后一次修改该记录的事务唯一标识。自增 |
  | DB_ROLL_PTR | **回滚指针**，指向该记录的上一个数据版本，与 undo log 配合实现事务回滚和 MVCC 多版本控制。 |
  | DB_ROW_ID   | 隐藏主键，当表未显式指定主键（PRIMARY KEY）且无唯一非空索引时，InnoDB 自动生成该字段（6 字节自增整数）。如果有，则不会添加该隐藏字段 |

  * undo log回滚日志，在insert、update、delete的时候产生的便于数据回滚的日志。

    * 当insert的时候，产生的undo log日志只在回滚时需要，在事务提交后，可被立即删除。
    * 而update、delete的时候，产生的undo log日志不仅在回滚时需要，在快照读时也需要，不会立即被删除。
    * 不同事务或相同事务对同一条记录进行修改，会导致该记录的undolog生成一条**记录版本链表**，链表的头部是最新的旧记录，链表尾部是最早的旧记录。---> undo log 版本链

  * **ReadView(读视图)**， 是快照读 SQL执行时MVCC提取数据的依据，记录并维护系统当前活跃的事务（未提交的）id。

    * ReadView中包含了四个核心字段：

    | 字段           | 含义                                                         |
    | -------------- | ------------------------------------------------------------ |
    | m_ids          | 当前活跃的事务 ID 集合（记录所有未提交的事务 ID）            |
    | min_trx_id     | 最小活跃事务 ID（m_ids 集合中最小的事务 ID）                 |
    | max_trx_id     | **预分配事务 ID**，即当前系统中最大的事务 ID + 1（因事务 ID 按自增规则生成） |
    | creator_trx_id | ReadView 创建者的事务 ID（即生成该读视图的事务自身 ID）      |

    * 而在readview中就规定了版本链数据的访问规则：trx_id 代表undolog版本链对应事务ID（被查询的undo log日志）

    | 条件                               | 是否可以访问该版本 | 说明                                                         |
    | ---------------------------------- | ------------------ | ------------------------------------------------------------ |
    | trx_id == creator_trx_id           | 可以访问           | 数据是当前事务自身修改的，对当前事务可见。                   |
    | trx_id < min_trx_id                | 可以访问           | 该版本对应的事务在所有活跃事务之前已提交，对当前事务可见。   |
    | trx_id > max_trx_id                | 不可以访问         | 该版本对应的事务是在 ReadView 生成后才开启的，对当前事务不可见。 |
    | min_trx_id <= trx_id <= max_trx_id | 视情况而定         | 若 trx_id 不在 m_ids 中（事务已提交），则可以访问；若在 m_ids 中（事务未提交），则不可访问。-->类似第二条 |

  > 不同的隔离级别，生成ReadView的时机不同：
  >
  > * READ COMMITTED ：在事务中每一次执行快照读时生成ReadView。
  >
  > * REPEATABLE READ：仅在事务中第一次执行快照读时生成ReadView，后续复用该ReadView。

## 3. 索引

​	索引（index）是帮助MySQL高效获取数据的数据结构(有序)。在数据之外，数据库系统还维护着满足特定查找算法的数据结构，这些数据结构以某种方式引用（指向）数据， 这样就可以在这些数据结构上实现高级查找算法，这种数据结构就是索引。

​	`mysql的索引是在存储层实现的，不同的存储引擎有不同的索引结构`

* 优势
  * 提高数据检索的效率，降低数据库的IO成本。
  * 通过索引列对数据进行排序，降低数据排序的成本，降低CPU的消耗。 
* 劣势
  * 索引大大提高了查询效率，同时却也降低更新表的速度， 如对表进行INSERT、UPDATE、DELETE时，效率降低。解释索引的优缺点并返回一张表
  * 索引也是要占据空间的

### B+树和B树

| 对比维度         | B 树（B-Tree）                                      | B + 树（B+ Tree）                                            |
| ---------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| 键值与数据存储   | 非叶子节点、叶子节点均存储真实键值和数据指针        | 非叶子节点仅存键值副本（索引），真实键值 + 数据指针仅在叶子节点 |
| 叶子节点特性     | 所有叶子节点在同一层，无链表连接                    | 所有叶子节点在同一层，通过双向链表有序连接                   |
| 范围查询效率     | 需逐层回溯查找，效率较低（O (log_m n + k)，含回溯） | 依托叶子节点链表，无需回溯，效率最优（O (log_m n + k)）      |
| 数据一致性       | 键值分散存储，更新时需同步非叶子节点，易冗余        | 数据仅存于叶子节点，更新无需同步索引层，无冗余               |
| 非叶子节点存储量 | 存储键值 + 数据指针，单节点存储键值数量较少         | 仅存储键值副本，单节点可存储更多键值，树高更低               |
| 单点查找路径     | 可能在非叶子节点找到目标并返回                      | 必须遍历至叶子节点，查找路径固定                             |
| 顺序访问支持     | 不支持高效顺序扫描，需从根节点重新遍历              | 叶子节点链表支持高效顺序扫描（如全表扫描）                   |
| 磁盘 I/O 效率    | 较高（树高低），但不及 B + 树                       | 更高（同阶下键值存储更多，树高更矮，I/O 次数更少）           |
| 典型应用场景     | 早期数据库索引、文件系统（如 EXT4、NTFS）           | 主流关系型数据库索引（MySQL InnoDB/MyISAM、PostgreSQL）      |

* MySQL索引数据结构对经典的B+Tree进行了优化。在原B+Tree的基础上，增加一个指向相邻叶子节点的链表指针，就形成了带有顺序指针的B+Tree，提高区间访问的性能，利于排序。

### hash

​	哈希索引就是采用一定的hash算法，将键值换算成新的hash值，映射到对应的槽位上，然后存储在hash表中。

* 特点：

  * A. Hash索引只能用于对等比较(=，in)，不支持范围查询（between，>，< ，...）

    B. 无法利用索引完成排序操作

    C. 查询效率高，通常(不存在hash冲突的情况)只需要一次检索就可以了，效率通常要高于B+tree索引（如果发生哈希碰撞，就需要线性探测再散列）4

* 存储引擎支持

  * 在MySQL中，支持hash索引的是Memory存储引擎。 而InnoDB中具有自适应hash功能，hash索引是InnoDB存储引擎根据B+Tree索引在指定条件下自动构建的。

### 思考题： 为什么InnoDB存储引擎选择使用B+tree索引结构?

​	A. 相对于二叉树，层级更少，搜索效率高；

​	B. 对于B-tree，无论是叶子节点还是非叶子节点，都会保存数据，这样导致一页中存储的键值减少，指针跟着减少，要同样保存大量数据，只能增加树的高度，导致性能降低；

​	C. 相对Hash索引，B+tree支持范围匹配及排序操作；

### 索引的分类

* 按功能：主键索引、唯一索引、普通索引、全文索引；
* 按存储：聚簇索引、非聚簇索引； ------> 聚簇索引和二级索引
* 按列数：单列索引、联合索引；
* 按结构：B + 树索引、哈希索引、空间索引。

​	实际使用中，需根据查询场景选择合适的索引类型，避免过度建索引（会降低插入 / 更新效率）。

## 5. 索引使用🌞🔥

#### 最左前缀法则

* 如果索引了多列（联合索引），要遵守最左前缀法则。最左前缀法则指的是查询从索引的最左列开始，并且不跳过索引中的列。如果跳跃某一列，索引将会部分失效(后面的字段索引失效)。

> 注意⚠️：最左前缀法则中指的最左边的列，是指在查询时，联合索引的最左边的字段(即是第一个字段)必须存在，与我们编写SQL时，条件编写的先后顺序无关。----人话，存在即可，顺序无关

#### 范围查询

* 联合索引中，出现范围查询(>,<)，范围查询右侧的列索引**失效**。
* 解释（存在一个表user的联合索引顺序为`idx_user_pro_age_sta`

```sql
-- 这句查询只会用到索引profession和age，因为age是范围查询(>)，所以后面的status索引失效了
explain select * from tb_user where profession = '软件工程' and age > 30 and status = '0';

-- 在业务允许的情况下，尽可能的使用类似于 >= 或 <= 这类的范围查询，而避免使用 > 或 <。
explain select * from tb_user where profession = '软件工程' and age >= 30 and status = '0'; -- 这样就不会失效
```

#### 索引失效情况

1. 索引进行了列运算

```sql
-- 不要在索引列上进行运算操作， 索引将失效。
explain select * from tb_user where substring(phone,10,2) = '15'; -- 索引phone失效
explain select * from tb_user where phone like '%17'; -- 同最左前缀原则，模糊匹配模糊左边索引失效

explain select * from tb_user where phone like '17%'; -- 但是模糊右边就不会失效哦！！！
```

2. 字符串不加引号

3. 头部模糊匹配

   * 如果仅仅是尾部模糊匹配，索引不会失效。如果是头部模糊匹配，索引失效。

4. `or`连接条件

   * 用or分割开的条件， 如果or前的条件中的列有索引，而后面的列中没有索引，那么涉及的索引都不会被用到。

     * 解释：`当or连接的条件，左右两侧字段都有索引时，索引才会生效`，而or只有一侧有索引，索引都不会生效

   * `and`关键字连接的索引只要存在就会生效！❌❌❌

     * ok，兄弟，大错特错

     ```sql
     -- 对于关键字and，必须是联合索引，and两边的两个索引才会都生效
     -- 如果and两边是两个单列索引，就只会生效一个，主键索引优先级最高，其他左优先（个屁，根据效率来的，主键效率最高）
     -- 如果and左右只存在一个索引，则会生效该索引
     -- 具体看后面的联合索引
     ```

     

5. 数据分布情况的影响

   * 一句话，`如果MySQL评估使用索引比全表更慢，则不使用索引。`---简而言之，就是取决于表中数据的分布情况走最优搜索
     * 因为如果走索引的话需要回表，也就是说查索引的时间分为两部分，查索引的和回表的，如果这两部分加起来耗时比全表扫描还高的话自然就用全表扫描了
   * 解释：（假设表user中的profession全部设置为null）

   ```sql
   -- 走全表扫描，因为大部分数据都是null，系统评估走全表扫描速度比索引更快
   explain select * from tb_user where profession is null; 
   -- 走索引，因为极少部分是非空值，系统认为走索引速度更快
   explain select * from tb_user where profession is not null;
   ```

### 5.1 SQL提示

* `use index` ： 建议MySQL使用哪一个索引完成此次查询（仅仅是建议，mysql内部还会再次进行评估）。

* `ignore index` ：告诉优化器 “排除指定索引”，并非强制禁止使用所有索引，而是**强制排除指定的索引**，但允许优化器从其他可用索引或全表扫描中选择执行计划。
* force index ： 强制使用索引。

```sql
explain select * from tb_user use index(idx_user_pro) where profession = '软件工程';
explain select * from tb_user ignore index(idx_user_pro) where profession = '软件工程';
explain select * from tb_user force index(idx_user_pro) where profession = '软件工程';
```

### 5.2 覆盖索引

* 覆盖索引关注的是选择展示的列（select后）的问题
* 覆盖索引是指 查询使用了索引，并且需要返回的列，在该索引中已经全部能够找到 。
* 如果select的数据有非索引列（因为走索引的话拿不到非索引列的数据需要回表，也就是说查索引的时间分为两部分，查索引的和回表的，时间更长）
* `尽量使用覆盖索引，减少select * ----> 减少回表查询的可能`

| 特征     | Using where; Using index                               | Using index condition                              |
| -------- | ------------------------------------------------------ | -------------------------------------------------- |
| 定义     | 使用了覆盖索引，查询所需数据均可从索引中获取，无需回表 | 使用了索引过滤条件，但仍需回表获取不在索引中的数据 |
| 回表操作 | 不需要                                                 | 需要                                               |
| 性能     | 更高（避免了回表的磁盘 I/O 操作）                      | 较低（需要回表查询）                               |
| 适用场景 | 查询的所有字段都包含在索引中                           | 查询的部分字段不在索引中，或有复杂条件需要索引过滤 |

* 解释：（假设存在user表的索引idx_user_name)

```sql
select id, name from tb_user where name = '王大伟'; -- 这是覆盖索引，不需要回表查询
select id, name, age from tb_user where name = '王大伟'; -- 需要回表查询获得age的数据 -- 怎么优化？

-- 建立idx_user_name_age的联合索引
create index idx_user_name_age on tb_user(name, age); -- 这样就能实现覆盖查询，无需回表
```

### 5.3 前缀索引

* 当字段类型为字符串（varchar，text，longtext等）时，有时候需要索引很长的字符串，这会让索引变得很大，查询时，浪费大量的磁盘IO， 影响查询效率。此时可以只将字符串的一部分前缀，建立索引，这样可以大大节约索引空间，从而提高索引效率。
* 前缀索引必然回表查询，因为索引字段不完整，必须返回聚簇索引获得完整的索引字段比对才能返回数据！！！
* 语法： `create index idx_xxxx on table_name(column(n)) ;`

```sql
-- 为tb_user表的email字段，建立长度为5的前缀索引
create index idx_email_5 on tb_user(email(5));
```

* 前缀长度
  * 可以根据索引的选择性来决定，而选择性是指**不重复的索引值（基数）和数据表的记录总数的比值**，索引选择性越高则查询效率越高。
  * 唯一索引的选择性是1，这是最好的索引选择性，性能也是最好的。

```sql
-- 求选择性的方法
select count(distinct email) / count(*) from tb_user ;
select count(distinct substring(email,1,5)) / count(*) from tb_user ;
```

* `substring(string, begin, end)` : 截取字符串string的从begin到end的子字符串
  * **索引计数**：SQL 中 `SUBSTRING` 的起始位置通常从 **1 开始**（与编程语言的 0 起始不同）。
  * **参数省略**：部分数据库（如 Oracle、MySQL）中，若省略 “长度” 参数，默认提取从起始位置到字符串末尾的所有字符。
  * **边界处理**：若指定的长度超过字符串剩余字符数，只会返回从起始位置到末尾的部分（不会报错）。

### 5.4 单列索引与联合索引

* 单列索引：即一个索引只包含单个列。
* 联合索引：即一个索引包含了多个列。列的顺序很重要（最左前缀原则），重复频率越低越要放在前面！

> 针对查询语句`select name, age from tb_user where name = '王大伟' and age = 21`

```sql
-- 如果name和age都是单列索引，那么mysql会根据哪一个的查询效率更高选择走单列查询--->必然是要回表查询的，没有实现覆盖查询
-- 可以通过建立name和age的联合索引，实现覆盖查询，但是现在存在name、age、name_age三个索引，所以必须使用sql提示认为选择效率更好的索引
```

* 在业务场景中，如果存在多个查询条件，考虑针对于查询字段建立索引时，**建议建立联合索引，而非单列索引。**

### 索引的设计原则

* 1). 针对于数据量较大，且查询比较频繁的表建立索引。一般来说数据量超过100多万算较大
* 2). 针对于常作为查询条件（where）、排序（order by）、分组（group by）操作的字段建立索引。联合索引！
* 3). 尽量选择区分度高的列作为索引，尽量建立唯一索引，区分度越高，使用索引的效率越高。
* 4). 如果是字符串类型的字段，字段的长度较长，可以针对于字段的特点，建立前缀索引。
* 5). 尽量使用联合索引，减少单列索引，查询时，联合索引很多时候可以覆盖索引，节省存储空间，避免回表，提高查询效率。
* 6). 要控制索引的数量，索引并不是多多益善，索引越多，维护索引结构的代价也就越大，会影响增删改的效率。
* 7). 如果索引列不能存储NULL值，请在创建表时使用NOT NULL约束它。当优化器知道每列是否包含NULL值时，它可以更好地确定哪个索引最有效地用于查询。

## 6. SQL优化

### 6.1 插入优化

* 如果我们需要一次性往数据库表中**插入多条记录**，可以从以下三个方面进行优化。

```sql
-- 优化方案一，批量插入数据; 不建议超过一千条
Insert into tb_test values(1,'Tom'),(2,'Cat'),(3,'Jerry');

-- 优化方案二，手动控制事务, 减少反复开启关闭事务
start transaction;
insert into tb_test values(1,'Tom'),(2,'Cat'),(3,'Jerry');
insert into tb_test values(4,'Tom'),(5,'Cat'),(6,'Jerry');
insert into tb_test values(7,'Tom'),(8,'Cat'),(9,'Jerry');
commit;

-- 主键顺序插入，性能要高于乱序插入。
-- 主键乱序插入 : 8 1 9 21 88 2 4 15 89 5 7 3
-- 主键顺序插入 : 1 2 3 4 5 7 8 9 15 21 88 89
```

* 大批量插入数据

  * 如果一次性需要插入大批量数据(比如: 几百万的记录)，使用insert语句插入性能较低，此时可以使用MySQL数据库提供的load指令进行插入。

  ```sql
  -- 客户端连接服务端时，加上参数 -–local-infile
  mysql –-local-infile -u root -p
  
  -- 设置全局参数local
  infile为1，开启从本地加载文件导入数据的开关
  set global local_infile = 1;
  
  -- 执行load指令将准备好的数据，加载到表结构中
  load data local infile '/root/sql1.log' into table tb_user fields terminated by ',' lines terminated by '\n' ;
  ```

  * `FIELDS TERMINATED BY ','`：定义文件中每条记录的字段之间用逗号（`,`）分隔。
  * `LINES TERMINATED BY '\n'`：定义文件中每条记录（行）之间用换行符（`\n`）分隔。
  * `load`导入数据同样遵守主键顺序插入性能高于乱序插入！

### 6.2 主键优化

* 数据组织方式：在InnoDB存储引擎中，表数据都是根据主键顺序组织存放的，这种存储方式的表称为索引组织表(index organized table IOT)。
  * 行数据，都是存储在聚集索引的叶子节点上的
  * 在InnoDB引擎中，数据行是记录在逻辑结构 page 页中的，而每一个页的大小是固定的，默认16K。那也就意味着， 一个页中所存储的行也是有限的，如果插入的数据行row在该页存储不小，将会存储到下一个页中，页与页之间会通过指针连接
  * 页可以为空，也可以填充一半，也可以填充100%。每个页包含了2-N行数据(如果一行数据过大，会行溢出)，根据主键排列
  * 页分裂和页合并
    * `MERGE_THRESHOLD`：合并页的阈值，可以自己设置，在创建表或者创建索引时指定。

* 索引设计原则
  * 满足业务需求的情况下，尽量**降低主键的长度**。（减少磁盘消耗）
  * 插入数据时，尽量选择**顺序插**入，选择使用AUTO_INCREMENT自增主键。（减少页分裂可能）
  * 尽量不要使用UUID做主键或者是其他自然主键，如身份证号。（主键顺序插入）
  * 业务操作时，避免对主键的修改。

### 6.3 order by 优化

* MySQL的排序，有两种方式：

  * `Using filesort` : 通过表的索引或全表扫描，读取满足条件的数据行，然后在**排序缓冲区sortbuffer中完成排序操作**，所有不是通过索引直接返回排序结果的排序都叫 FileSort 排序。

  * `Using index`: 通过有序索引顺序扫描直接返回有序数据，这种情况即为 using index，不需要额外排序，操作效率高。

* 对于以上的两种排序方式，Using index的性能高，而Using filesort的性能低，我们在优化排序操作时，尽量要优化为 Using index。

  

  * 在explain语句输出包含排序的查询语句中，Extra中出现了`Backward index scan`，这个代表**反向扫描索引**

    * 必须是覆盖查询，而且order by的所有字段都是desc降序
    * 因为在MySQL中我们创建的索引，默认索引的叶子节点是从小到大排序的，而此时我们查询排序时，是从大到小，所以，在扫描时，就是反向扫描，就会出现 Backward index scan。 在MySQL8版本中，支持降序索引，我们也可以创建降序索引

  * 排序时,也需要**满足最左前缀法则**,否则也会出现 filesort

  * ### `Using index; Using filesort`: 输出Using index是覆盖查询，Using filesort说明联合索引和排序顺序不同，此时索引的有序性无法直接利用，MySQL 需先通过索引获取数据（因覆盖索引显示 `Using index`），再将数据放入内存或临时文件中重新排序（因此显示 `Using filesort`）。

```sql
-- 创建联合索引(age 升序排序，phone 倒序排序)
create index idx_user_age_phone_ad on tb_user(age asc ,phone desc);
```

* order by优化原则:

  * A. 根据排序字段建立合适的索引，多字段排序时，也**遵循最左前缀法则**。

  * B. 尽量使用覆盖索引。

  * C. 多字段排序, 一个升序一个降序，此时需要注意联合索引在创建时的规则（ASC/DESC）。

  * D. 如果不可避免的出现filesort，大数据量排序时，可以适当增大排序缓冲区大小sort_buffer_size(默认256k)。

### 6.4 group by 优化

* group by 的优化类似order by，同样可以通过**索引提升效率**；也必须**满足最左前缀原则**
* 相对using index; using filesort的是group by 中如果存在`idx_name_age`的索引，那么`group by age`（只要排序顺序跟联合索引不一样）
  * `using index; using temporary`：using index表示是覆盖查询；using yemporary表示无法直接利用索引的有序性分组，需要建立一张**临时表**

### 6.5 limit 优化

* 在数据量比较大时，如果进行limit分页查询，在查询时，越往后，分页查询效率越低。

> `select * from tb_user limit 90000000, 10`

* 针对上面这条查询，此时需要MySQL排序前90000010 记录，仅仅返回 90000000 - 90000010 的记录，其他记录丢弃，查询排序的代价非常大

```sql
-- 优化思路: 一般分页查询时，通过创建 覆盖索引 能够比较好地提高性能，可以通过 覆盖索引 加 子查询 形式进行优化
-- 老版本的数据库不支持limit 在子查询中～～
select * from tb_sku where id in (select id from tb_sku order by id limit 90000000, 10);

-- 联合查询优化limit
explain select t.* from tb_sku t , (select id from tb_sku a order by id limit 9000000000,10) a where t.id = a.id; -- id是主键或者存在以id为二级索引，就是覆盖查询
```

### 6.6 count 优化

> select count(*) from tb_user ;

* MyISAM 引擎把一个表的总行数存在了磁盘上，因此执行 count(*) 的时候会直接返回这个数，效率很高； 但是如果是带条件的count，MyISAM也慢。*
* *InnoDB 引擎就麻烦了，它执行 count(*) 的时候，需要把数据一行一行地从引擎里面读出来，然后累积计数。
* 如果说要大幅度提升InnoDB表的count效率，主要的优化思路：**自己计数** (可以借助于redis这样的数据库进行,但是如果是带条件的count又比较麻烦了)。

#### count的用法

* count() 是一个聚合函数，对于返回的结果集，一行行地判断，如果 count 函数的参数不是NULL，累计值就加 1，否则不加，最后返回累计值。
* 用法：count（*）、count（主键）、count（字段）、count（数字）

| COUNT 用法    | 含义                                          | InnoDB 引擎处理逻辑                                          |
| ------------- | --------------------------------------------- | ------------------------------------------------------------ |
| `count(主键)` | 统计主键字段非 NULL 的行数（主键默认非 NULL） | 遍历整张表，取出每一行的主键值返回给服务层，服务层直接按行累加（主键不会为 NULL） |
| `count(字段)` | 统计指定字段非 NULL 的行数                    | - 字段无 NOT NULL 约束：遍历表取出字段值，服务层判断是否为 NULL，非 NULL 则累加 - 字段有 NOT NULL 约束：遍历表取出字段值，服务层直接按行累加 |
| `count(数字)` | 统计所有行数（数字代表常量，如 `count(1)`）   | 遍历整张表但不取值，服务层对每一行放入一个数字（如 1），直接按行累加，～这个数字好想没啥意义～ |
| `count(*)`    | 统计所有行数（包括 NULL 行）                  | InnoDB引擎并不会把全部字段取出来，而是专门做了优化，不取值，服务层直接按行进行累加。 |

> 按照效率排序的话，count(字段) < count(主键 id) < count(1) ≈ count(*)，所以尽量使用 count(*)。

### 6.7 update 优化

* **InnoDB的行锁是针对索引加的锁，不是针对记录加的锁 ,并且该索引不能失效，否则会从行锁升级为表锁 。**

```sql
 -- 主键索引，行级锁不会影响update的并发性，也就是说两个终端可以同时针对couse表的行级数据进行修改更新
update course set name = 'javaEE' where id = 1 ;

-- 但是如果name没有建立索引，那么现在就是表锁，在这个更新提交事务之前，所有其他的更新该表的操作都不允许
update course set name = 'SpringBoot' where name = 'PHP' ;
```

* 因此，尽量根据主键或者索引字段进行数据的更新

## 7. 视图

### 7.1 视图

* 视图（View）是一种虚拟存在的表。视图中的数据并不在数据库中实际存在，行和列数据来自定义视图的查询中使用的表（基表），并且是在使用视图时动态生成的。

* 通俗的讲，视图只保存了查询的SQL逻辑，不保存查询结果。所以我们在创建视图的时候，主要的工作就落在创建这条SQL查询语句上。

​	在 MySQL 中，视图（View）是一种虚拟表，它基于 SQL 查询的结果集，并不实际存储数据。视图可以简化复杂查询、提高数据安全性（限制用户访问特定列）和增强数据独立性。以下是 MySQL 中视图的主要语法：

#### 1. 创建视图

```sql
CREATE [OR REPLACE] VIEW 视图名 [(列名1, 列名2, ...)]
AS
SELECT 查询语句
[WITH （ cascaded | local ） CHECK OPTION];
```

- `OR REPLACE`：如果视图已存在，则替换它
- `(列名1, 列名2, ...)`：可选，指定视图列名，若不指定则使用查询结果的列名
- `WITH CHECK OPTION`：确保对视图的更新操作符合视图定义的条件

示例：

```sql
-- 创建一个显示学生基本信息的视图
CREATE VIEW student_info AS
SELECT id, name, age, gender
FROM students
WHERE status = 1;
```

#### 2. 查询视图

**视图的查询与表的查询语法相同**：

```sql
SELECT * FROM 视图名 WHERE 条件;
```

示例:

```sql
SELECT name, age FROM student_info WHERE gender = '男';
```

#### 3. 修改视图

有两种方式修改视图：

- 方式一（替换视图）：

```sql
CREATE OR REPLACE VIEW 视图名 AS
新的SELECT查询语句;
```

- 方式二：

```sql
ALTER VIEW 视图名 [(列名1, 列名2, ...)]
AS
新的SELECT查询语句
[WITH CHECK OPTION];
```

#### 4. 删除视图

```sql
DROP VIEW [IF EXISTS] 视图名;
```

`IF EXISTS` 用于避免删除不存在的视图时出现错误

#### 5. 查看视图信息

- 查看所有视图：

```sql
SHOW TABLES;  -- 视图会和表一起显示
```

- 查看特定视图定义：

```sql
SHOW CREATE VIEW 视图名; -- 查看视图的创建语句
```

- 从系统表中查询视图信息：

```sql
SELECT * FROM information_schema.views WHERE table_name = '视图名';
```

### 注意事项：

1. 视图可以嵌套，即一个视图可以基于另一个视图创建
2. 并非所有视图都可更新，当视图包含以下情况时通常不可更新：
   - 使用 `DISTINCT` 关键字
   - 使用聚合函数（`SUM`, `COUNT`, `AVG` 等）或者窗口函数
   - 使用 `GROUP BY` 或 `HAVING`
   - 使用 `UNION` 或 `UNION ALL`
   
   > **要使视图可更新，视图中的行与基础表中的行之间必须存在一对一的关系**
   
3. `WITH CHECK OPTION` 确保通过视图插入或更新的数据仍能被视图查询到

通过合理使用视图，可以简化复杂的数据库操作，同时提高数据访问的安全性和一致性。

### 7.2 视图检查选项的补充

* 当使用WITH CHECK OPTION子句创建视图时，MySQL会通过视图检查正在更改的每个行，例如 插入，更新，删除，以使其符合视图的定义。
* MySQL允许基于另一个视图创建视图，它还会检查依赖视图中的规则以保持一致性。
* 为了确定检查的范围，mysql提供了两个选项： CASCADED 和 LOCAL，默认值为 CASCADED 。

#### 不加视图检查选项

* 如果没有视图检查选项，插入数据如果超出视图的判断条件，仍然会插入表中，但是数据不会在视图上显示！这非常危险⚠️（也就是说，不加检查选项，插入数据就不会判断**建立视图的语句的判断条件**直接插入）

#### 默认cascaded检查（级联）

```sql
create or replace view t_1 as select id from test where id <= 15;
create or replace view t_2 as select id from t_1 where id > 6 with check option ;
create or replace view t_3 as select id from t_2 where id < 11 ;
```

* t_1视图不加检查选项，表示不管插入什么数据，都能直接插入表中，但是只能显示 id 小于等于 15 的数据
* t_2视图建立在t_1视图上，那么插入数据不仅要考虑t2的条件，也要考虑t1的条件（**不管t1表有没有检查约束**）
  * 也就是说，t_2视图只能接受插入 6 < id <= 15 的数据；但是不影响插入t1的数据判断条件（也就是没有条件）
  * 在这个情况下，向t1插入id = 35，能插入，但是不会在t1视图显示，也就不会在t2视图显示；向t2插入id = 3/16，都会报错；向t2插入id = 14，在表中、t1、t2都会显示
* 在t_2的基础上建立t_3视图，id的取值范围是 6 < id <= 15,同t_2，因为t3表没有检查约束，但是会向上一级表检查，t2表有检查选项，所以t3表的约束继承自t2
  * 那么现在插入数据从上到下：t_1~(没有条件)，t_2~(6 < id <=15)，t_3~(6 < id <= 15)
  * 在这个基础上，如果把t2的约束去掉，给t1加上约束，那么插入数据从上到下：t_1~(id <= 15)，t_2~(id <= 15)，t_3~(id <= 15)

#### local检查选项

```sql
create or replace view t_1 as select id from test where id <= 15  ;
create or replace view t_2 as select id from t_1 where id > 6 with local check option ;
create or replace view t_3 as select id from t_2 where id < 19 with local check option ;
```

* 一句话，插入数据从上至下：t_1~(没有条件)，t_2~(6 < id)，t_3～(6 < id < 19)
  * 如果把t_2改成cascaded，t_3的where id < 12, 那么从上到下插入数据：t_1~(没有条件)，t_2~(6 < id <= 15)，t_3~(6 < id <= 12)

> 可以理解为，`cascaded`是强制向上级联，而`local`是**上级存在检查约束**（不管什么约束）才会向上级联

### 7.3 视图的作用

1). 简单：视图不仅可以简化用户对数据的理解，也可以简化他们的操作。那些被经常使用的查询可以被定义为视图，从而使得用户不必为以后的操作每次指定全部的条件。

2). 安全：数据库可以授权，但不能授权到数据库特定行和特定的列上。通过视图用户只能查询和修改他们所能见到的数据

3). 数据独立：视图可帮助用户屏蔽真实表结构变化带来的影响。

> ～感觉视图就是把临时表存储起来的一种操作～

## 8. 存储过程

​	MySQL 存储过程是一种在数据库中存储复杂程序、供外部程序调用的数据库对象，它由一组预先编译好的 SQL 语句组成，类似于编程语言中的函数。下面详细解释 MySQL 存储过程的核心概念、特点、语法及使用场景：

### **一、存储过程的基本概念**

​	存储过程（Stored Procedure）是在 MySQL 中创建并保存的一段 SQL 代码集合，可包含查询、插入、更新、删除等操作，还能实现流程控制（如条件判断、循环）。创建后，用户可以通过调用存储过程名称来执行这段代码，无需每次重新编写 SQL。

​	存储过程是事先经过编译并存储在数据库中的一段 SQL 语句的集合，调用存储过程可以简化应用开发人员的很多工作，减少数据在数据库和应用服务器之间的传输，对于提高数据处理的效率是有好处的。存储过程思想上很简单，就是数据库 SQL 语言层面的代码封装与重用。

### **二、存储过程的特点**

1. **预编译执行**

   存储过程在创建时会被编译，后续调用时无需重新编译，执行效率更高（尤其适合复杂逻辑）。

2. **代码复用与维护**

   一次创建，多次调用，减少重复编写 SQL 的工作量；修改存储过程即可统一更新逻辑，便于维护。

3. **减少网络传输**

   若需执行多条 SQL，直接调用存储过程只需传输调用命令，而非所有 SQL 语句，降低网络开销。

4. **增强安全性**

   可通过授权让用户调用存储过程，但限制其直接访问底层表，保护数据安全。

5. **支持流程控制**

   可使用 `IF...ELSE`、`CASE`、`LOOP`、`WHILE` 等语句实现复杂业务逻辑。

* 简单记：封装、复用；可以接受参数，也可以返回参数；减少网络交互，效率提升

### **三、存储过程的语法**

#### **1. 创建存储过程**

基本语法：

```sql
DELIMITER //  -- 修改分隔符（避免与 SQL 中的分号冲突） -- 实际上这是在命令行才需要改，在datagrip不需要✅
CREATE PROCEDURE 存储过程名(参数列表)
BEGIN
    -- SQL 语句和流程控制逻辑
END //
DELIMITER ;  -- 恢复默认分隔符
```

> 注意：在命令行中，执行创建存储过程的SQL时，需要通过关键字 `delimiter` 指定SQL语句的结束符。

- **参数列表**：可选，格式为 `[IN|OUT|INOUT] 参数名 数据类型`
  - `IN`：输入参数（默认，调用时传入值，过程内不可修改）
  - `OUT`：输出参数（过程内修改值，调用后可获取结果）
  - `INOUT`：既作为输入，也作为输出

示例：创建一个查询指定用户信息的存储过程

```sql
DELIMITER //
CREATE PROCEDURE GetUserById(IN userId INT)
BEGIN
    SELECT * FROM users WHERE id = userId;
END //
DELIMITER ;
```

#### **2. 调用存储过程**

使用 `CALL` 语句调用：

```sql
CALL 存储过程名(参数);
```

示例：调用上述存储过程查询 ID 为 1 的用户

```sql
CALL GetUserById(1);
```

若有输出参数，需先用变量接收：

```sql
-- 示例：创建带输出参数的存储过程 -- 这里不改结束符
CREATE PROCEDURE GetUserCount(OUT total INT)
BEGIN
    SELECT COUNT(*) INTO total FROM users;
END;

-- 调用并获取结果
SET @count = 0;
CALL GetUserCount(@count);
SELECT @count;  -- 输出用户总数
```

#### **3. 查看存储过程**

- 查看所有存储过程：

  ```sql
  SHOW PROCEDURE STATUS;
  ```

- 查看指定存储过程的创建语句：

  ```sql
  SHOW CREATE PROCEDURE 存储过程名;
  ```

- 查询指定数据库的存储过程及状态信息

  ```sql
  SELECT * FROM INFORMATION_SCHEMA.ROUTINES WHERE ROUTINE_SCHEMA = 'xxx'; -- xxx是数据库名字
  ```

#### **4. 修改与删除存储过程**

- MySQL 不支持直接修改存储过程内容，需先删除再重建。

- 删除存储过程：

  ```sql
  DROP PROCEDURE IF EXISTS 存储过程名;
  ```

### **四、存储过程的流程控制**

存储过程支持多种流程控制语句，实现复杂逻辑：

1. **条件判断**

   ```sql
   DELIMITER //
   CREATE PROCEDURE CheckAge(IN age INT)
   BEGIN
       IF age >= 18 THEN
           SELECT '成年人' AS result;
       ELSE
           SELECT '未成年人' AS result;
       END IF;
   END //
   DELIMITER ;
   ```

2. **循环（WHILE）**

   ```sql
   DELIMITER //
   CREATE PROCEDURE InsertNumbers(IN n INT)
   BEGIN
       DECLARE i INT DEFAULT 1;
       WHILE i <= n DO
           INSERT INTO numbers (num) VALUES (i);
           SET i = i + 1;
       END WHILE;
   END //
   DELIMITER ;
   ```

3. **异常处理**

   使用 `DECLARE HANDLER` 捕获异常：

   ```sql
   DELIMITER //
   CREATE PROCEDURE SafeDelete(IN id INT)
   BEGIN
       DECLARE EXIT HANDLER FOR SQLEXCEPTION
       BEGIN
           SELECT '删除失败' AS message;
       END;
       
       DELETE FROM users WHERE id = id;
       SELECT '删除成功' AS message;
   END //
   DELIMITER ;
   ```

### **五、存储过程的优缺点**

#### **优点**

- 提高执行效率（预编译）。
- 减少网络传输，适合大量 SQL 操作。
- 集中管理业务逻辑，便于维护。
- 增强安全性，限制直接表访问。

#### **缺点**

- 调试困难（MySQL 对存储过程的调试支持较弱）。
- 可移植性差（不同数据库的存储过程语法差异大）。
- 过度使用可能导致数据库压力增大（逻辑集中在数据库层）。

### **六、适用场景**

- 复杂的业务逻辑（如订单处理、数据统计）。
- 频繁执行的 SQL 操作（如批量插入、定时任务）。
- 需要限制用户直接访问表的场景（通过存储过程间接操作）。

### **总结**

MySQL 存储过程是封装 SQL 逻辑的有效工具，适合处理复杂、高频的数据库操作，能提升效率和安全性，但需权衡其调试难度和可移植性问题。合理使用可显著优化数据库层的设计与性能。

## 9. 变量

​	在 MySQL 中，变量是用于存储数据的命名容器，可在 SQL 语句、存储过程、函数等数据库操作中使用。MySQL 中的变量主要分为**系统变量**和**用户变量**两大类，此外还有**局部变量**（在存储程序中使用）。下面详细解释这些变量的特点和使用方法：

### 一、系统变量（System Variables）

​	系统变量是 MySQL 服务器内置的变量，用于控制服务器的运行行为和配置参数。它们由服务器自动维护，可通过修改部分系统变量来调整数据库的性能或行为。

#### 1. 系统变量的分类

- **全局变量（Global Variables）**：影响整个 MySQL 服务器的运行，对所有连接有效。修改后通常需要重启服务器或通过 `SET GLOBAL` 生效（部分变量支持动态修改）。
- **会话变量（Session Variables）**：仅对当前数据库连接（会话）有效，不同会话的变量值相互独立。修改后立即在当前会话生效，不影响其他会话。

#### 2. 查看系统变量

使用 `SHOW VARIABLES` 命令查看所有系统变量，或通过 `LIKE` 筛选特定变量：

```sql
-- 查看所有系统变量
SHOW VARIABLES;

-- 查看包含 "max_connections" 的变量（全局/会话）
SHOW VARIABLES LIKE 'max_connections';

-- 查看全局变量（需 SUPER 权限）
SHOW GLOBAL VARIABLES LIKE 'innodb_buffer_pool_size';

-- 查看当前会话变量
SHOW SESSION VARIABLES LIKE 'sql_mode';

-- 确定变量名的情况下
SELECT @@[SESSION | GLOBAL] 系统变量名; -- 查看指定变量的值
```

#### 3. 修改系统变量

通过 `SET` 命令修改系统变量，需注意作用范围（全局 / 会话）：

```sql
-- 修改全局变量（对新会话生效，当前会话不生效 ---> 针对版本，但是大概率是都生效的！）
SET GLOBAL max_connections = 1000;

-- 修改会话变量（仅当前会话生效）
SET SESSION sql_mode = 'STRICT_TRANS_TABLES';

-- 简化写法（默认作用于会话）
SET autocommit = 0;
```

> mysql服务重新启动之后，所设置的全局参数会失效，要想不失效，可以在 /etc/my.cnf 中配置。

#### 4. 常用系统变量示例

- `max_connections`：允许的最大并发连接数（全局）。
- `innodb_buffer_pool_size`：InnoDB 存储引擎的缓冲池大小（全局，影响性能）。
- `sql_mode`：SQL 模式，控制 SQL 语法校验和数据验证规则（全局 / 会话）。
- `autocommit`：是否自动提交事务（会话，默认 ON）。

### 二、用户变量（User-Defined Variables）

用户变量是用户自定义的变量，用户变量不用提前声明，用于在当前会话中临时存储数据，作用范围仅限当前连接（会话结束后失效）。

#### 1. 定义和赋值

用户变量以 `@` 开头，无需声明类型，直接赋值即可：

```sql
-- 赋值方式1：使用 SET 命令
SET @user_name = 'Alice';
SET @age := 30;  -- 也可使用 := 赋值（在 SQL 语句中推荐）

-- 赋值方式2：在 SQL 语句中通过 SELECT 赋值
SELECT @total := COUNT(*) FROM users;
SELECT name INTO @first_user FROM users LIMIT 1;
```

> 注意：`=` 在 `SET` 中是赋值运算符，但在 `SELECT` 中是比较运算符，因此在 `SELECT` 中赋值需用 `:=`。（其实都可以，但是区分）

#### 2. 使用用户变量

用户变量可在 SQL 语句（SELECT、INSERT、UPDATE 等）中直接使用：

```sql
-- 在 SELECT 中使用
SELECT @user_name, @age;

-- 在条件中使用
SELECT * FROM users WHERE age > @age;

-- 在 UPDATE 中使用
UPDATE users SET score = score + 10 WHERE name = @user_name;
```

> 注意: 用户定义的变量无需对其进行声明或初始化，只不过未初始化的变量获取到的值为NULL，不会报错

#### 3. 特点

- 作用域：仅当前会话，其他会话无法访问。
- 类型：动态类型，根据赋值自动转换（如字符串、数字、NULL 等）。
- 生命周期：会话结束后自动释放，无需手动删除。

### 三、局部变量（Local Variables）

局部变量是**在存储程序（存储过程、函数、触发器）中声明的变量**，作用范围仅限程序内部的 BEGIN...END 块，需显式声明类型。（访问之前，需要`DECLARE`声明。可用作存储过程内的局部变量和输入参数）

#### 1. 声明和使用

局部变量无需 `@` 前缀，需用 `DECLARE` 声明，且必须在程序开始处声明：

```sql
DELIMITER // -- 在datagrip里这一步不是必须

CREATE PROCEDURE get_user_count()
BEGIN
  -- 声明局部变量（必须在 BEGIN 后第一行）
  DECLARE total INT DEFAULT 0;  -- 声明并初始化
  
  -- 赋值
  SELECT COUNT(*) INTO total FROM users;
  
  -- 使用
  SELECT total AS user_count;
END //

DELIMITER ;
call get_user_count(); -- 执行存储过程
```

#### 2. 特点

- 作用域：仅限声明它的 BEGIN...END 块（或嵌套的子块）。
- 类型：必须指定数据类型（如 INT、VARCHAR 等）。
- 生命周期：随存储程序的执行结束而释放。

### 四、变量的区别与使用场景

| 变量类型     | 声明方式           | 作用范围                  | 前缀 | 典型使用场景                     |
| ------------ | ------------------ | ------------------------- | ---- | -------------------------------- |
| 全局系统变量 | 服务器内置         | 整个 MySQL 服务器         | 无   | 调整服务器配置（如连接数、缓存） |
| 会话系统变量 | 服务器内置         | 当前会话                  | 无   | 临时修改当前会话的 SQL 模式等    |
| 用户变量     | SET 或 SELECT 赋值 | 当前会话                  | @    | 会话内临时存储中间结果           |
| 局部变量     | DECLARE 声明       | 存储程序的 BEGIN...END 块 | 无   | 存储程序内部的临时计算           |

### 五、注意事项

1. 系统变量的修改权限：修改全局变量通常需要 `SUPER` 权限，会话变量一般不需要特殊权限。
2. 用户变量的大小写：在 MySQL 中，用户变量名不区分大小写（`@name` 和 `@NAME` 是同一个变量）。
3. 局部变量的作用域：若在嵌套块中声明同名变量，内层变量会覆盖外层变量。
4. 性能影响：频繁使用用户变量可能影响查询优化器的判断，复杂场景下建议使用局部变量或临时表。

通过合理使用 MySQL 中的变量，可以灵活地控制服务器行为、存储临时数据，提高 SQL 脚本和存储程序的可读性与效率。

## 10. 流程控制

### 1. IF（条件判断语句）

**含义**：根据条件执行不同代码分支，基础条件控制结构。

**语法**：

```sql
IF 条件1 THEN
    语句块1;
[ELSEIF 条件2 THEN
    语句块2;]  -- 可选，可多个
[ELSE
    语句块3;]  -- 可选，所有条件不满足时执行
END IF;
```

**使用方法**：

- 条件为布尔表达式（如 `a > 10`、`b IS NULL`）。
- 条件 1 成立则执行语句块 1；否则判断条件 2，以此类推；所有条件不成立时执行 ELSE 块（若有）。

**示例**：

```sql
DELIMITER //
CREATE PROCEDURE check_score(score INT) -- 默认参数是in类型
BEGIN
    IF score >= 90 THEN
        SELECT '优秀' AS result;
    ELSEIF score >= 60 THEN
        SELECT '及格' AS result;
    ELSE
        SELECT '不及格' AS result;
    END IF;
END //
DELIMITER ;

-- 调用
CALL check_score(85);  -- 输出：优秀
```

### 2. 参数（Parameter）

**含义**：在存储过程 / 函数与外部传递数据的变量，分输入、输出、输入输出参数。

**语法**（MySQL 存储过程）：

```sql
CREATE PROCEDURE 过程名(
    参数1 [IN/OUT/INOUT] 数据类型 [DEFAULT 默认值],
    参数2 [IN/OUT/INOUT] 数据类型 [DEFAULT 默认值]
)
BEGIN
    -- 过程体
END;
```

- `IN`：输入参数（默认），外部传入值，过程内不可修改。
- `OUT`：输出参数，过程内赋值，外部通过变量接收结果。
- `INOUT`：既输入又输出，外部传入初始值，过程内可修改并返回。

**示例**：

```sql
DELIMITER //
CREATE PROCEDURE add_num(
    IN a INT,
    IN b INT,
    OUT result INT
)
BEGIN
    SET result = a + b;
END //
DELIMITER ;

-- 调用（需用变量接收OUT参数）
SET @res = 0;
CALL add_num(3, 5, @res);
SELECT @res;  -- 输出：8
```

### 3. CASE（多条件分支语句）

**含义**：多条件判断，类似 `IF-ELSEIF-ELSE`，适合单一变量多值判断。

**语法**：

- 简单 CASE（变量与值匹配）：

  ```sql
  CASE 变量
      WHEN 值1 THEN 结果1;
      WHEN 值2 THEN 结果2;
      ...
      [ELSE 结果N;]  -- 可选，无匹配时执行
  END CASE;
  ```

- 搜索 CASE（条件表达式判断）：

  ```sql
  CASE
      WHEN 条件1 THEN 结果1;
      WHEN 条件2 THEN 结果2;
      ...
      [ELSE 结果N;]
  END CASE;
  ```

**使用方法**：

- 简单 CASE 适用于变量等于固定值的场景；搜索 CASE 适用于复杂条件。
- 执行第一个匹配的分支，无匹配且无 ELSE 时会报错。

**示例**：

```sql
DELIMITER //
CREATE PROCEDURE check_day(day INT)
BEGIN
    CASE day
        WHEN 1 THEN SELECT '周一' AS day_name;
        WHEN 2 THEN SELECT '周二' AS day_name;
        WHEN 3 THEN SELECT '周三' AS day_name;
        ELSE SELECT '其他' AS day_name;
    END CASE;
END //
DELIMITER ;

CALL check_day(3);  -- 输出：周三
```

### 4. WHILE（条件循环语句）

**含义**：条件满足时重复执行循环体，先判断条件再执行（可能一次不执行）。

**语法**：

```sql
WHILE 条件 DO
    循环体语句;
    [IF 退出条件 THEN LEAVE; END IF;]  -- 可选，提前退出（用LEAVE）
END WHILE;
```

**使用方法**：

- 循环前先检查条件，为真则执行循环体，执行后再次检查，直到条件为假退出。
- 可用 `LEAVE` 配合条件提前退出循环（避免死循环）。

**示例**：

```sql
DELIMITER //
CREATE PROCEDURE loop_while()
BEGIN
    DECLARE i INT DEFAULT 1;
    WHILE i <= 5 DO
        SELECT i;
        SET i = i + 1;
    END WHILE;
END //
DELIMITER ;

CALL loop_while();  -- 输出1到5
```

### 5. REPEAT（直到型循环）

**含义**：先执行一次循环体，再判断条件，直到条件满足时退出（至少执行一次）。

**语法**：

```sql
REPEAT
    循环体语句;
UNTIL 退出条件  -- 条件满足时退出
END REPEAT;
```

**使用方法**：

适用于循环体至少执行一次的场景，执行后检查条件，满足则退出。

**示例**：

```sql
DELIMITER //
CREATE PROCEDURE loop_repeat()
BEGIN
    DECLARE i INT DEFAULT 1;
    REPEAT
        SELECT i;
        SET i = i + 1;
    UNTIL i > 5  -- i>5时退出
    END REPEAT;
END //
DELIMITER ;

CALL loop_repeat();  -- 输出1到5
```

### 6. LOOP（无限循环）

**含义**：无初始条件的循环，需在循环体内通过 `LEAVE` 手动控制退出，否则为死循环。

**语法**：

```sql
循环标签: LOOP  -- 需定义标签用于LEAVE
    循环体语句;
    IF 退出条件 THEN
        LEAVE 循环标签;  -- 退出循环
    END IF;
END LOOP 循环标签;
```

* `ITERATE`：用在循环中，作用是跳过当前循环剩下的语句，直接进入下一次循环。 --> 类似continue

**使用方法**：

适用于循环次数不确定，但可通过事件（如数据读取完毕）触发退出的场景。

**示例**：

```sql
DELIMITER //
CREATE PROCEDURE loop_even_with_iterate()
BEGIN
    DECLARE i INT DEFAULT 1;
    loop_label: LOOP  -- 定义循环标签
        -- 如果是奇数，直接跳过本次循环（不输出），进入下一次
        IF i % 2 != 0 THEN
            SET i = i + 1;  -- 先自增
            ITERATE loop_label;  -- 跳过当前循环，进入下一次🌟
        END IF;
        
        -- 到这里说明是偶数，执行输出
        SELECT i;
        SET i = i + 1;
        
        -- 当i超过10时退出循环
        IF i > 10 THEN
            LEAVE loop_label;
        END IF;
    END LOOP loop_label;
END //
DELIMITER ;

CALL loop_even_with_iterate();  -- 输出2,4,6,8,10
```

### 7. 游标（Cursor）

**含义**：用于在存储过程中逐行**处理查询结果集**的对象，类似指针指向结果集中的行。（就是存储一行的多个数据或者一张表的指针，是为了传递给变量，而变量不可能一次赋值多个数据）

**语法**：

```sql
-- 1.声明游标
DECLARE 游标名 CURSOR FOR SELECT 语句; 

-- 声明游标结束标志（必选，用于判断是否结束）
DECLARE CONTINUE HANDLER FOR NOT FOUND SET 标志变量 = 1; -- 这个也是条件处理程序的内容

-- 使用游标
OPEN 游标名;  -- 2.打开游标，执行查询

FETCH 游标名 INTO 变量列表;  -- 3.提取当前行数据到变量

WHILE 标志变量 = 0 DO  -- 标志为0表示有数据
    -- 处理数据
    FETCH 游标名 INTO 变量列表;  -- 移动到下一行
END WHILE;

CLOSE 游标名;  -- 4.关闭游标，释放资源
```

> ```sql
> DECLARE CONTINUE HANDLER FOR NOT FOUND SET 标志变量 = 1;
> 
> WHILE 标志变量 = 0 DO 
>     FETCH 游标名 INTO 变量列表;  
> END WHILE;
> ```
>
> * 当fetch读取数据没有时，条件处理程序会设置变量为1并继续盖程序，由于变量不再为0所以不会再读取数据，退出循环

**使用方法**：

* 需逐行处理查询结果时使用，通过 `CONTINUE HANDLER` 捕获 “无数据” 事件，**避免游标溢出错误**。

**示例**：

```sql
DELIMITER //
CREATE PROCEDURE get_emp_names(dept_no INT)
BEGIN
    DECLARE v_ename VARCHAR(20); -- ⚠️必须要先声明局部变量，再声明游标，最后声明处理程序
    DECLARE done INT DEFAULT 0;  -- 结束标志，//初始化为 0（表示默认有数据）
    -- 声明游标，//获取数据
    DECLARE emp_cursor CURSOR FOR
        SELECT ename FROM emp WHERE deptno = dept_no;
    -- 绑定结束事件，//就是条件处理程序
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1;
    
    OPEN emp_cursor; -- 🍉
    fetch_loop: LOOP
        FETCH emp_cursor INTO v_ename;
        IF done = 1 THEN
            LEAVE fetch_loop;  -- 无数据时退出
        END IF;
        SELECT v_ename;  -- 输出姓名
    END LOOP fetch_loop;
    CLOSE emp_cursor; -- 🍉
END //
DELIMITER ;

-- 调用（假设emp表存在deptno=30的员工）
CALL get_emp_names(30);
```

> 关于⚠️的解释：这是因为游标依赖于已经声明的变量（游标定义中可能用到变量），而处理程序通常需要引用游标或变量，所以必须放在最后。变量声明 → 游标声明 → 处理程序声明，这一顺序不可颠倒，否则会导致存储过程创建失败。

### 8. 条件处理程序（Condition Handler）

**含义**：捕获并处理存储过程执行中的错误（如除零、数据不存在），避免程序异常终止。用来定义在流程控制结构执行过程中遇到问题时相应的处理步骤。

**语法**：

```sql
DECLARE 处理类型 HANDLER FOR 异常类型
BEGIN
    -- 异常处理逻辑
END; -- //这一段就是处理程序，可以自己写，begin和end好像可以省略
```

- 处理类型：`CONTINUE`（继续执行当前程序）或 `EXIT`（退出当前块，终止执行当前程序）。
- 异常类型：
  - 具体错误码（如 `1048` 表示非空约束错误）
    - MySQL 为每种错误分配了唯一数字编码，可直接通过错误码捕获特定错误。
  - `SQLSTATE` 码（如 `'23000'` 表示约束冲突）；如`02000`表示无数据（与 `NOT FOUND` 等价，常用于游标遍历结束）
    - SQLSTATE 是标准化的错误代码（5 个字符），同一类错误可能对应多个具体错误码。
  - `NOT FOUND`（游标无数据）。所有以02开头的SQLSTATE代码的简写
    - 是 `SQLSTATE '02000'` 的别名，专门用于捕获**游标遍历结束**或 `SELECT ... INTO` 未找到数据的情况。
  - `SQLWARNING`: 所有以01开头的SQLSTATE代码的简写
  - `SQLEXCEPTION`: 所有没有被SQLWARNING 或 NOT FOUND捕获的SQLSTATE代码的简写
  - `SQLEXCEPTION`（所有异常），通用异常类型，可捕获**所有未被特定处理的错误**

**常见异常场景**：

- 除零错误（`SQLSTATE '22012'`）。
- 数据不存在（`NOT FOUND`）。
- 主键冲突（`SQLSTATE '23000'`）。

**示例**

```sql
DELIMITER //
CREATE PROCEDURE divide_num(a INT, b INT)
BEGIN
    DECLARE result INT;
    -- 捕获除零错误（SQLSTATE '22012'）
    DECLARE EXIT HANDLER FOR SQLSTATE '22012'
    BEGIN
        SELECT '错误：除数不能为零' AS error_msg;
    END;
    
    SET result = a / b;
    SELECT result AS division_result;
END //
DELIMITER ;

CALL divide_num(10, 0);  -- 输出：错误：除数不能为零
```

以上是 MySQL 存储过程中核心控制结构的语法和用法，与 PL/SQL 相比，MySQL 更依赖 `DELIMITER` 定义分隔符，且异常处理通过 `DECLARE HANDLER` 实现，游标必须配合 `NOT FOUND` 处理器使用。

### 9. 存储函数 🌞

​	在 MySQL 中，存储函数（Stored Function）是一种存储在数据库中的可重用 SQL 代码块，它接受参数、执行特定操作并返回一个单一值。存储函数与存储过程类似，但主要区别在于存储函数必须返回一个值，而存储过程可以返回多个值或不返回值。

#### 存储函数的特点

1. **返回值**：必须通过`RETURN`语句返回一个值，且返回值的数据类型在定义时指定。有返回值的存储过程
2. **参数**：可以接受输入参数（`IN`类型），但**不能有输出参数**（`OUT`或`INOUT`）。
3. **可调用性**：可以在 SQL 语句（如`SELECT`、`INSERT`等）中直接调用，如同内置函数一样。
4. **封装性**：将复杂逻辑封装起来，提高代码复用性和维护性。
5. **权限**：创建存储函数需要`CREATE ROUTINE`权限，执行需要`EXECUTE`权限。

#### 存储函数的语法结构：

```sql
DELIMITER //
CREATE FUNCTION 函数名(参数1 数据类型, 参数2 数据类型, ...)
RETURNS 返回数据类型 [characteristic ...]
BEGIN
    -- 函数体（SQL语句）
    RETURN 返回值;
END //
DELIMITER ;
```

#### 关于[characteristic ...]说明

* characteristic说明：

  * DETERMINISTIC：相同的输入参数总是产生相同的结果

  * NO SQL ：不包含 SQL 语句。

  * READS SQL DATA：包含读取数据的语句，但不包含写入数据的语句。

> 在mysql8.0版本中binlog默认是开启的，一旦开启了，mysql就要求在定义存储过程时，需要指定characteristic特性，否则就会报错误

#### 示例

创建一个计算两个数之和的存储函数：

```sql
DELIMITER //
CREATE FUNCTION add_two_numbers(a INT, b INT)
RETURNS INT DETERMINISTIC
BEGIN
    DECLARE result INT;  -- 声明局部变量
    SET result = a + b;
    RETURN result;
END //
DELIMITER ;
```

调用该函数：

```sql
SELECT add_two_numbers(5, 3);  -- 结果为8
```

* 适用场景：

  - 简化复杂的计算逻辑，如数据转换、公式计算等。

  - 在查询中重复使用同一逻辑，减少代码冗余。

  - 提高执行效率，因为存储函数在数据库服务器端执行，减少网络传输。

* 注意事项：

  - 存储函数不能包含`INSERT`、`UPDATE`、`DELETE`等修改数据的语句（除非使用`DETERMINISTIC`并确保函数不修改数据）。

  - 若函数可能修改数据或返回不确定结果，需谨慎使用，可能影响查询优化器的判断。

  - 可以使用`DROP FUNCTION 函数名;`删除存储函数。

## 11. 触发器

​	MySQL 触发器（Trigger）是一种特殊的存储程序，它会在指定的数据库事件发生时（之前或之后）自动执行，无需手动调用。触发器通常与表关联，当对表执行 INSERT、UPDATE 或 DELETE 操作时被触发。

### 触发器的主要特点

1. **自动执行**：当满足触发条件时，触发器会自动运行，无需用户干预
2. **与表关联**：触发器总是依附于某个表，不能独立存在
3. **响应特定事件**：只能对 INSERT、UPDATE、DELETE 三种操作做出响应（不能对查询做响应）
4. 现在触发器还**只支持行级触发**，不支持语句级触发。

### 触发器的语法结构🌟

```sql
CREATE TRIGGER 触发器名称
触发时间（BEFORE/AFTER）触发事件（INSERT/UPDATE/DELETE）
ON 表名 FOR EACH ROW -- 行级触发器
BEGIN
    -- 触发器执行的SQL语句
END;
```

#### 关键参数说明

- **触发时间**：
  - `BEFORE`：在事件发生之前执行
  - `AFTER`：在事件发生之后执行
- **触发事件**：
  - `INSERT`：插入记录时触发
  - `UPDATE`：更新记录时触发
  - `DELETE`：删除记录时触发
- **FOR EACH ROW**：表示对每一行数据都触发一次（触发器没有表级触发）

#### 特殊关键字

- `OLD`：表示被操作的原记录（仅用于 UPDATE 和 DELETE）🍎 在插入操作中old没用
- `NEW`：表示新插入或更新后的记录（仅用于 INSERT 和 UPDATE）🍌在删除操作中new没用

### 应用场景示例

1. **数据验证**：在插入或更新前检查数据有效性
2. **日志记录**：自动记录对重要数据的修改操作
3. **数据同步**：当一个表的数据变化时，自动更新关联表
4. **默认值设置**：在插入前为某些字段设置默认值

### 示例：创建一个简单的触发器

```sql
-- 为用户表创建更新日志触发器 -- 通常一个更新日志表需要增删查三个触发器
CREATE TRIGGER user_update_log
AFTER UPDATE ON users FOR EACH ROW
BEGIN
    INSERT INTO user_logs (user_id, action, old_name, new_name, change_time)
    VALUES (OLD.id, 'UPDATE', OLD.name, NEW.name, NOW());
END;
```

这个触发器会在 `users` 表中的记录被更新后，自动在 `user_logs` 表中插入一条日志记录，保存修改前后的用户名和修改时间。

### 管理触发器的**语法**🌟

- 查看触发器：`SHOW TRIGGERS;`
- 删除触发器：`DROP TRIGGER [IF EXISTS] [schema_name] trigger_name;` -- 如果没有指定数据库，默认当前数据库

触发器虽然强大，但过度使用可能会影响数据库性能，增加维护复杂度，因此应谨慎使用。

## 12. 锁🔒

​	锁是计算机协调多个进程或线程并发访问某一资源的机制。在数据库中，除传统的计算资源（CPU、RAM、I/O）的争用以外，数据也是一种供许多用户共享的资源。如何保证数据并发访问的一致性、有效性是所有数据库必须解决的一个问题，锁冲突也是影响数据库并发访问性能的一个重要因素。从这个角度来说，锁对数据库而言显得尤其重要，也更加复杂。

#### 一、锁的核心分类（按粒度）

- **表锁**：锁定整个数据表，开销小、加锁快，并发度低。MyISAM 存储引擎默认使用，InnoDB 也支持（如 `LOCK TABLES` 语句）。
- **行锁**：锁定单条数据行，开销大、加锁慢，并发度高。InnoDB 存储引擎默认使用，是高并发场景的首选。
- **页锁**：介于表锁和行锁之间，锁定数据页（MySQL 中一页默认 16KB），并发度中等，仅部分存储引擎（如 BDB）支持。

#### 二、锁的性质分类（按读写权限）

- **共享锁（S 锁，读锁）**：多个事务可同时加锁，仅允许读操作，禁止写操作。通过 `SELECT ... LOCK IN SHARE MODE` 手动添加。
- **排他锁（X 锁，写锁）**：仅允许一个事务加锁，同时禁止其他事务加共享锁和排他锁，支持读写操作。InnoDB 写操作（INSERT/UPDATE/DELETE）会自动加排他锁。

#### 三、关键辅助锁（InnoDB 特有）

- **意向锁**：表级锁，用于快速判断表中是否有行锁，避免全表扫描检查。分为意向共享锁（IS 锁）和意向排他锁（IX 锁），由 InnoDB 自动添加。
- **间隙锁（Gap 锁）**：锁定索引区间，防止幻读（事务重复查询时结果集变化），仅在 InnoDB RR（可重复读）隔离级别下生效。
- **临键锁（Next-Key 锁）**：间隙锁 + 行锁的组合，是 InnoDB RR 级别下的默认行锁算法，覆盖索引区间及边界行。

#### 四、不同存储引擎的锁特性对比

| 存储引擎 | 支持的锁类型                 | 锁粒度默认值 | 并发性能 | 适用场景                         |
| -------- | ---------------------------- | ------------ | -------- | -------------------------------- |
| MyISAM   | 表锁、S/X 锁                 | 表锁         | 低       | 读多写少（如静态数据查询）       |
| InnoDB   | 行锁、表锁、意向锁、间隙锁等 | 行锁         | 高       | 读写并发（如电商订单、用户数据） |

#### 五、锁的核心作用

- 解决并发问题：防止脏读、不可重复读、幻读（通过锁与事务隔离级别配合）。
- 保障数据一致性：避免多个事务同时修改同一数据导致的数据冲突。

### 一、全局锁（Global Lock）

#### 定义

全局锁是锁定**整个 MySQL 实例**的锁，加锁后所有数据库的所有表都处于只读状态（无法执行写操作，如 `INSERT/UPDATE/DELETE`、表结构修改等），直至锁释放。

#### 核心作用

- **全库备份**：确保备份期间数据一致性（避免备份时同时有写操作导致数据混乱）。
- **全局数据一致性维护**：如跨库事务的数据同步场景。

#### 语法

```sql
FLUSH TABLES WITH READ LOCK; -- 枷锁，执行后，所有表被锁定为只读，新的写操作会阻塞，已执行的写事务会被等待。
UNLOCK TABLES; -- 解锁，释放全局锁，数据库恢复读写能力。
```

#### 注意事项

- **性能影响**：加锁期间全库只读，对业务写入影响极大，仅建议在短时间备份或维护时使用。
- **替代方案**：InnoDB 可通过 `mysqldump --single-transaction` 结合事务快照实现无锁备份（依赖 MVCC），无需全局锁。

> 数据备份语法：`mysqldump -u用户 –p密码 要备份的数据库 > 备份位置`
>
> Eg：`mysqldump --single-transaction -uroot –p123456 itcast > D:/itcast.sql`

### 二、表级锁（Table-Level Lock）

#### 定义

表级锁是锁定**整张表**的锁，粒度比全局锁小，比行级锁大。加锁 / 解锁效率高，但并发度较低（同一时间仅允许有限的锁冲突操作）。锁定粒度大，发生锁冲突的概率最高，并发度最低。

#### 支持的存储引擎

- MyISAM、MEMORY 等存储引擎默认使用表级锁；
- InnoDB 也支持表级锁（但默认优先使用行级锁）。

#### 分类及语法

1. **表共享锁（Table Read Lock，读锁）**

   - 作用：多个事务可同时加读锁，仅允许读操作，禁止写操作（包括当前事务）。/也叫表共享读锁

   - 语法：`LOCK TABLES 表名 [, 表名2...] READ;`

   - 示例：

     ```sql
     LOCK TABLES user READ; -- 锁定 user 表为读锁
     SELECT * FROM user; -- 允许读
     UPDATE user SET name='a' WHERE id=1; -- 报错（读锁禁止写）
     UNLOCK TABLES; -- 解锁 // 客户端断开连接也会释放锁
     ```

2. **表排他锁（Table Write Lock，写锁）**

   - 作用：仅当前事务可加写锁，拥有读写权限，其他事务的读写操作均被阻塞。/也叫表独占锁

   - 语法：`LOCK TABLES 表名 [, 表名2...] WRITE;`

   - 示例：

     ```sql
     LOCK TABLES user WRITE; -- 锁定 user 表为写锁
     UPDATE user SET name='a' WHERE id=1; -- 允许写
     SELECT * FROM user; -- 允许读
     -- 其他事务执行 SELECT/UPDATE 会阻塞，直至解锁
     UNLOCK TABLES; -- 解锁
     ```

     > ⚠️ 排他锁在解锁时，其他进程被阻塞的操作会执行而不是终止！

3. **意向锁（Intention Lock，InnoDB 特有）**

   - 作用：表级锁，用于快速判断表中是否有行锁（避免全表扫描检查行锁），由 InnoDB 自动添加，无需手动操作。

   - // 解决表级锁和行级锁之间加锁的冲突问题

   - 分类：

     - 意向共享锁（IS）：事务计划对表中某些行加共享锁；
       - 声明：事务计划对表中的某些行加**行级共享锁（S 锁）**（如执行 `SELECT ... LOCK IN SHARE MODE`）。
       - 触发：当事务执行 `SELECT ... LOCK IN SHARE MODE` 前，InnoDB 会自动为表加 IS 锁。
       - 与表锁共享锁(read)兼容，与表锁排他锁(write)互斥。
     - 意向排他锁（IX）：事务计划对表中某些行加排他锁。
       - 声明：事务计划对表中的某些行加**行级排他锁（X 锁）**（如执行 `INSERT/UPDATE/DELETE` 或 `SELECT ... FOR UPDATE`）。
       - 触发：当事务执行写操作或手动加行级 X 锁前，InnoDB 会自动为表加 IX 锁。
       - 与表锁共享锁(read)及排他锁(write)都互斥，意向锁之间不会互斥。

     > 一旦事务提交，意向共享锁、意向排他锁都会自动释放

4. **元数据锁**

​	元数据锁（MDL，Metadata Lock）是 MySQL 保护表结构的核心锁，核心结论是：MDL 是表级元数据锁，用于防止 “表结构修改” 与 “表数据读写” 并发冲突，自动加锁 / 释放，**无需手动操作，仅在事务结束或语句执行完毕后释放。** // 解决DDL与DML语句的冲突

* 元数据锁的作用：

  * 主要就是一句话：为了避免DML语句（数据操作）与DDL（数据定义）冲突，保证读写的正确性

  * 保护表元数据一致性：表元数据包括表结构（字段、索引、引擎等）、表属性（字符集、注释等）。

  * 避免并发冲突：**防止一个事务在读写数据时，另一个事务修改表结构**（如 `ALTER TABLE`），导致数据读写异常（如字段不存在、索引失效）。

* 锁冲突规则
  * 多个读操作可同时加 MDL 读锁（互不阻塞）。
  * 读操作与写操作（表结构修改）互斥：读锁存在时，表结构修改会阻塞；表结构修改时，所有读写操作会阻塞。
  * 多个表结构修改操作互斥（同一时间仅允许一个执行）。

### 三、行级锁（Row-Level Lock）

#### 定义

行级锁是锁定**表中单行数据**的锁，粒度最小，并发度最高（仅锁定修改的行，不影响其他行），是 InnoDB 存储引擎的核心锁机制。

#### 核心特点

- 依赖索引：若查询条件未使用索引，行锁会升级为表锁（因为无法定位具体行）。
- 与事务绑定：锁的生命周期与事务一致（事务提交 / 回滚后自动释放）。
- InnoDB的数据是基于索引组织的，行锁是通过对索引上的索引项加锁来实现的，而不是对记录加的锁。

#### 分类（黑马）

* 行锁（Record Lock）：锁定单个行记录的锁，防止其他事务对此行进行update和delete。在RC（read commited）、RR（repeatable read，默认）隔离级别下都支持。
* 间隙锁（Gap Lock）：锁定索引记录间隙（不含该记录），确保索引记录间隙不变，防止其他事务在这个间隙进行insert，产生幻读。在RR隔离级别下都支持。
* 临键锁（Next-Key Lock）：行锁和间隙锁组合，同时锁住数据，并锁住数据前面的间隙Gap。在RR隔离级别下支持。

#### 分类及语法

1. **行共享锁（Row Share Lock，S 锁）**

   - 作用：多个事务可同时对同一行加 S 锁，仅允许读操作，禁止写操作。 // 可以不同会话一起读一行

   - 语法：`SELECT ... LOCK IN SHARE MODE;`（需在事务中执行）

   - 示例：

     ```sql
     BEGIN; -- 开启事务
     -- 对 id=1 的行加 S 锁
     SELECT * FROM user WHERE id=1 LOCK IN SHARE MODE;
     -- 其他事务可加 S 锁（共享读），但加 X 锁（写）会阻塞
     COMMIT; -- 提交事务释放锁
     ```

2. **行排他锁（Row Exclusive Lock，X 锁）**

   - 作用：仅允许一个事务对行加 X 锁，拥有读写权限，其他事务的 S 锁和 X 锁均被阻塞。// 一行在修改，就不允许其他会话操作这一行

   - 语法：`SELECT ... FOR UPDATE;`（手动加锁）；InnoDB 的 `INSERT/UPDATE/DELETE` 会自动加 X 锁。

   - 示例：

     ```sql
     BEGIN;
     -- 对 id=1 的行加 X 锁
     SELECT * FROM user WHERE id=1 FOR UPDATE;
     UPDATE user SET name='b' WHERE id=1; -- 基于锁定行修改
     -- 其他事务对 id=1 的行读写均阻塞
     COMMIT; -- 释放锁
     ```

| SQL 操作语句                    | 行锁类型       | 加锁方式                           |
| ------------------------------- | -------------- | ---------------------------------- |
| INSERT ...                      | 排他锁（X 锁） | 自动加锁，无需手动干预             |
| UPDATE ...                      | 排他锁（X 锁） | 自动加锁，无需手动干预             |
| DELETE ...                      | 排他锁（X 锁） | 自动加锁，无需手动干预             |
| SELECT（正常查询，无额外语法）  | 无             | 不加任何锁                         |
| SELECT ...` LOCK IN SHARE MODE` | 共享锁（S 锁） | 手动加锁，需在 SELECT 后添加该语法 |
| SELECT ... `FOR UPDATE`         | 排他锁（X 锁） | 手动加锁，需在 SELECT 后添加该语法 |

3. **间隙锁（Gap Lock）与临键锁（Next-Key Lock，InnoDB 特有）**

- 间隙锁：锁定索引区间（如 `WHERE id BETWEEN 5 AND 10` 会锁定 (5,10) 区间），**防止幻读**，仅在 `REPEATABLE READ`（RR）隔离级别生效。
- 临键锁：间隙锁 + 行锁的组合，是 RR 级别下的默认行锁算法（锁定区间及边界行）。锁定当前数据记录以及之前部分的间隙
- 无需手动加锁，由 InnoDB 自动触发。

* 默认情况下，InnoDB在`REPEATABLE READ`事务隔离级别运行，InnoDB使用 next-key 锁进行搜索和索引扫描，以防止幻读。

  * 索引上的等值查询(唯一索引)，给不存在的记录加锁时, 优化为间隙锁 。

  * 索引上的等值查询(非唯一普通索引)，向右遍历时最后一个值不满足查询需求时，next-keylock 退化为间隙锁。

  * 索引上的范围查询(唯一索引)--会访问到不满足条件的第一个值为止。

  * --->以上的各种情况都是在查询的时候给查询值以及前后间隙上锁，防止幻读

> 注意：间隙锁唯一目的是防止其他事务插入间隙，造成幻读。间隙锁可以共存，一个事务采用的间隙锁不会阻止另一个事务在同一间隙上采用间隙锁。

### 三类锁的对比总结

| 锁类型 | 锁定粒度        | 加锁效率 | 并发度 | 适用场景                  | 典型操作语法                  |
| ------ | --------------- | -------- | ------ | ------------------------- | ----------------------------- |
| 全局锁 | 整个 MySQL 实例 | 高       | 极低   | 全库备份、全局一致性维护  | `FLUSH TABLES WITH READ LOCK` |
| 表级锁 | 整张表          | 高       | 中     | 读多写少场景（如 MyISAM） | `LOCK TABLES ... READ/WRITE`  |
| 行级锁 | 单行数据        | 低       | 高     | 读写并发场景（如 InnoDB） | `SELECT ... FOR UPDATE` 等    |

> 针对唯一索引进行检索时，对已存在的记录进行等值匹配时，将会自动优化为行锁。
>
> ⚠️**InnoDB的行锁是针对于索引加的锁，不通过索引条件检索数据，那么InnoDB将对表中的所有记录加锁，此时 就会升级为表锁。**

实际开发中，InnoDB 的行级锁是主流选择（平衡并发与一致性），表级锁和全局锁仅在特定场景下使用（如 MyISAM 表、全库备份）。需特别注意行级锁对索引的依赖，避免因索引失效导致锁升级。

## 13. 数据库管理

### 系统数据库

​	mysql数据库安装完成后，自带了四个数据库，具体如下：

| 数据库             | 含义                                                         |
| ------------------ | ------------------------------------------------------------ |
| mysql              | 存储 MySQL 服务器正常运行所需要的各种信息（如时区、主从配置、用户账号、权限设置等）。 |
| information_schema | 提供访问数据库元数据（数据库本身的数据）的表和视图，包含数据库名、表名、字段类型、数据类型、访问权限等元信息。 |
| performance_schema | 为 MySQL 服务器运行时状态提供**底层监控功能**，主要用于收集数据库服务器的性能参数（如锁等待、线程状态、资源消耗等）。 |
| sys                | 包含一系列基于 performance_schema 的视图，方便 DBA 和开发人员进行性能调优与诊断（简化性能数据的查询和分析）。 |

* 这些系统数据库是 MySQL 自身运行和管理的核心，其中 `information_schema` 和 `sys` 常用于日常元数据查询和性能分析，`mysql` 库用于用户与权限管理，`performance_schema` 多用于底层性能监控。

### mysql常用工具

#### mysql

* 该mysql不是指mysql服务，而是指**mysql的客户端工具**。

* 语法：`mysql [options] [database]`

  * 选项：
    * -u，--user=name，指定用户名
    * -p，--password[=name]，指定密码
    * -h，--host=name ，指定服务器IP或域名
    * -P，-port=port ，指定连接端口
    * -e，--execute=name ，执行SQL语句并退出

  > -e选项可以在Mysql客户端执行SQL语句，而不用连接到MySQL数据库再执行，对于一些批处理脚本，这种方式尤其方便

  * 事例：以root用户在3306端口查询远程客户端（指定IP地址）的数据库itcast下的表stu的数据，数据库密码是1234
    * `mysql -h192.168.1.2 -P3306 -p1234 -uroot itcast -e "select * from stu"`--> 无需登陆连接数据库直接查询到数据

#### mysqladmin

* mysqladmin 是一个**执行管理操作的客户端程序**。可以用它来检查服务器的配置和当前状态、创建并删除数据库等。
* 通过帮助文档查看选项：`mysqladmin --help`
* 选项同上一个工具，⚠️这些工具都是在命令行中用的～

```cmd
mysqladmin -root -p1234 version // 查看数据库版本
mysqladmin -root -p1234 variables //查看系统变量
mysqladmin -root -p1234 create db01 //创建数据库db01
mysqladmin -root -p1234 drop db01 // 删除数据库db01
```

#### mysqlbinlog

* 由于服务器生成的二进制日志文件以二进制格式保存，所以如果想要**检查这些文本的文本格式**，就会使用到mysqlbinlog 日志管理工具。
* 语法：`mysqlbinlog [options] log-files1 log-files2 ...`
  * 选项 ：
    * -d，--database=name 指定数据库名称，只列出指定的数据库相关操作。
    * -o，--offset=# 忽略掉日志中的前n行命令。
    * -r，--result-file=name 将输出的文本格式日志输出到指定文件。
    * -s，--short-form 显示简单格式， 省略掉一些信息。
    * --start-datatime=date1 --stop-datetime=date2 指定日期间隔内的所有日志。
    * --start-position=pos1 --stop-position=pos2 指定位置间隔内的所有日志

#### mysqlshow

* mysqlshow 客**户端对象查找工具**，用来很快地查找存在哪些数据库、数据库中的表、表中的列或者索引。
* 语法：`mysqlshow [options] [db_name [table_name [col_name]]]`
  * 选项：
    * --count， 显示数据库及表的统计信息
    * -i，显示指定的数据库或者指定表的状态信息

```cmd
mysqlshow -uroot -p1234 db01 --count // 显示db01数据库的统计情况
mysqlshow -uroot -p1234 db01 course --count //显示db01数据库下course表的详细字段情况
mysqlshow -uroot -p1234 db01 course id --count // 显示db01数据库下course表的id字段信息
```

#### mysqldump

* mysqldump 客户端工具用来**备份数据库或在不同数据库之间进行数据迁移**。备份内容包含创建表，及插入表的SQL语句。
* 语法：

| 语法格式                                             | 说明                                                     |
| ---------------------------------------------------- | -------------------------------------------------------- |
| `mysqldump [options] db_name [tables]`               | 备份指定数据库中的指定表（若不指定表，则备份整个数据库） |
| `mysqldump [options] --database/-B db1 [db2 db3...]` | 备份一个或多个指定数据库（包含数据库创建语句）           |
| `mysqldump [options] --all-databases/-A`             | 备份 MySQL 服务器上的所有数据库                          |

* 连接选项同上

* 输出选项：

  | 选项语法               | 说明                                                         |
  | ---------------------- | ------------------------------------------------------------ |
  | `--add-drop-database`  | 在每个数据库创建语句前添加 `DROP DATABASE` 语句（确保重建时先删除旧库） |
  | `--add-drop-table`     | 在每个表创建语句前添加 `DROP TABLE` 语句（默认开启，禁用需用 `--skip-add-drop-table`） |
  | `-n, --no-create-db`   | 备份中不包含数据库的创建语句（`CREATE DATABASE`）            |
  | `-t, --no-create-info` | 备份中不包含数据表的创建语句（`CREATE TABLE`），仅保留数据   |
  | `-d, --no-data`        | 备份中不包含数据，仅保留数据库和表的结构语句                 |
  | `-T, --tab=name`       | 自动生成两个文件：- `.sql` 文件：存储表结构（`CREATE TABLE` 语句）- `.txt` 文件：存储表数据（纯文本格式，按行分隔）// 这个好 |

* 事例：
  * 备份单个库并包含删除旧表语句：`mysqldump -u root -p --add-drop-table testdb > testdb_backup.sql`
  * 仅备份表结构（不含数据）：`mysqldump -u root -p -d testdb > testdb_structure.sql`

#### mysqlimport/source

| 导入工具 / 指令 | 核心用途                                   | 语法格式                                                 | 示例                                                         |
| --------------- | ------------------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------ |
| mysqlimport     | 导入 `mysqldump -T` 导出的文本文件（.txt） | `mysqlimport [options] db_name textfile1 [textfile2...]` | `mysqlimport -uroot -p2143 test /tmp/city.txt`（导入 test 库，使用 /tmp 目录下的 city.txt 文本文件） |
| source          | 导入 SQL 脚本文件（.sql）                  | `source 本地SQL文件路径;`                                | `source /root/backup_testdb.sql;`（在 MySQL 命令行中执行，导入指定路径的 SQL 文件） |

* 补充说明：

  - `mysqlimport` 是 MySQL 客户端命令（需在操作系统终端执行），仅支持文本文件导入，且文本文件需与表结构对应（字段顺序、分隔符一致）。注意这里导入的文本文件要在受mysql信任的文件路径下`/var/lib/mysql-files/`

  - `source` 是 MySQL 命令行内部指令（需先登录 MySQL 再执行），仅支持 SQL 文件导入，适用于恢复 `mysqldump` 导出的完整备份（含表结构 + 数据）。在那个数据库使用这个命令就导入那个数据库
