# 计算机网络体系结构

计算机网络体系结构是将网络功能划分为**分层的模块结构**，通过各层协议实现特定功能，层间通过接口传递数据，从而降低网络设计的复杂度。主流的体系结构有**OSI 七层模型**（ISO 制定）和**TCP/IP 四层模型**（实际工业标准）。

## 一、OSI 七层模型（ISO）分层及详情表

| **分层**   | **核心功能**                                                 | **数据单元**             | **典型协议 / 技术**       | **关键作用**                                                 |
| ---------- | ------------------------------------------------------------ | ------------------------ | ------------------------- | ------------------------------------------------------------ |
| 应用层     | 为应用程序提供网络服务，直接对接用户业务需求                 | 报文                     | HTTP、FTP、SMTP、DNS      | 实现网页访问、文件传输、邮件收发、域名解析等具体网络应用     |
| 表示层     | 负责数据格式转换、加密解密、压缩解压缩，统一通信双方的数据编码格式 | 报文                     | JPEG、ASCII、SSL/TLS      | 解决不同系统间数据格式不兼容问题，保障数据传输的安全性和可读性 |
| 会话层     | 建立、管理和终止表示层之间的通信会话，提供会话同步和断点续传功能 | 报文                     | RPC、NetBIOS、PPTP        | 控制通信会话的生命周期，避免数据传输过程中出现会话中断或数据混乱 |
| 传输层     | 实现端到端的通信，提供可靠 / 不可靠传输，处理流量控制和差错恢复 | 段（TCP）/ 数据报（UDP） | TCP、UDP、SPX             | 保障应用程序之间数据传输的可靠性和效率，区分同一主机的不同应用进程 |
| 网络层     | 负责跨网络的分组转发和路由选择，实现逻辑地址（IP）寻址       | 分组 / 数据报            | IP、ICMP、ARP、OSPF       | 打通不同子网的通信链路，确定数据传输的最优路径，完成源主机到目的主机的寻址 |
| 数据链路层 | 将网络层分组**封装为帧**，实现相邻节点间的可靠传输，处理物理层的传输差错 | 帧                       | Ethernet、PPP、MAC        | 负责同一链路内节点间的帧传输，进行帧校验和差错重传，定义物理地址（MAC 地址） |
| 物理层     | 定义物理介质的电气、机械特性，**实现比特流的传输，规定接口标准** | 比特                     | 双绞线、光纤、无线 802.11 | 完成二进制比特流的物理传输，是整个网络体系的硬件基础         |

| **分层**         | **核心功能**                                                 | **数据单元**             | **典型协议 / 技术**           | **对应 OSI 分层**        |

#### 传输层：端到端

* 复用和分用

  * 复用（从上到下）：在发送数据的时候，同一台主机上的多个进程可以使用同一个传输层协议
  * 分用（从下到上）：在接收数据的时候，传输层可以把数据正确交付到目的进程

* 差错检测

  - TCP 检测出差错后丢弃数据，并通知发送方重传
  - UDP 检测出差错后直接丢弃数据，且不通知发送方

  

* 向应用层提供服务 🔥

  - TCP 提供面向连接的、可靠的、面向字节流的端到端传输服务：
    - 确保数据正确 / 完善，但开销大，实时性较差
    - 面向连接：也可以叫有连接，传输前先打招呼，先确认对方已经准备好接收数据，传输结束时也要告诉对方已结束
    - 可靠：接收方使用 “确认机制” 让发送方知道哪些数据已被正确接收
    - 面向字节流：无论传输多少个报文，在 TCP 协议看来都是一连串字节流
  - UDP 提供无连接的、不可靠的、面向报文的端到端传输服务：
    - 数据可能出错 / 丢失，但速度快，开销小
    - 无连接：不打招呼，直接把数据传给对方
    - 不可靠：接收方无论收没收到数据、数据是否正确，都不给发送方反馈
    - 面向报文：UDP 不能拆分数据报，只能传输整个数据报

###### 传输层寻址与端口

* 通过端口号标识本主机的一个特定进程

  * 每台主机的端口号是相互独立的
  * TCP、UDP 两种协议的端口号是相互独立的

  * TCP 或 UDP 协议，通过 **Socket 套接字**，唯一地标识网络中的一台主机上的一个应用进程
    * 套接字（Socket）= {IP 地址：端口号}
    * 本质上是一种数据结构，类似于网络指针，指向网络中将要和本进程通信的进程
  * 当两个进程之间想要通信时，需要指明：
    * 使用哪种传输层协议
    * 本进程绑定的端口号
    * 对方的 IP 地址和端口号

## UDP协议

UDP（User Datagram Protocol，用户数据报协议）是 TCP/IP 协议簇中**无连接、不可靠**的传输层协议，它的核心特点是轻量、高效，适用于对实时性要求高、可容忍少量数据丢失的场景。

#### UDP 的核心特性

1. **无连接性**

   - UDP 通信前不需要建立连接（不像 TCP 的 “三次握手”），通信双方无需维护连接状态。
   - 发送方直接将数据封装成数据报后发送，接收方也无需确认连接，直接接收数据报。
   - 通信结束后也没有 “四次挥手” 的断开流程，开销极低。

2. **不可靠性**

   - **无确认机制**：发送方发送数据后，不会收到接收方的确认，无法知道数据是否送达。
   - **无重传机制**：数据报丢失、损坏时，UDP 不会自动重传。
   - **无顺序保证**：若发送多个数据报，接收方可能乱序接收，UDP 不负责排序。
   - **无流量控制和拥塞控制**：发送方不会根据网络状况调整发送速率，可能导致网络拥塞或数据丢失。

3. **面向数据报**

   - UDP 以**数据报**为基本传输单位，每个数据报都是独立的，发送方一次发送一个数据报，接收方一次接收一个完整的数据报（要么全收，要么全丢），不能拆分或合并。
   - 数据报的大小受限于网络 MTU（最大传输单元），超过 MTU 会被 IP 层分片，增加丢失风险。

4. **头部开销小**

   - UDP 头部仅**8 字节**，远小于 TCP 的 20 字节（最小头部），格式如下：

     | 字段       | 长度   | 说明                       |
     | ---------- | ------ | -------------------------- |
     | 源端口号   | 2 字节 | 发送方端口（可选，可为 0） |
     | 目的端口号 | 2 字节 | 接收方应用程序端口         |
     | 数据报长度 | 2 字节 | 头部 + 数据的总字节数      |
     | 校验和     | 2 字节 | 用于校验数据完整性（可选） |

5. 支持一对一（封装成单播 IP 数据报）、一对多（封装成广播 / 多播 IP 数据报）传输

## TCP协议

TCP（Transmission Control Protocol，传输控制协议）是 TCP/IP 协议簇中**面向连接、可靠**的传输层协议，其核心目标是在不可靠的 IP 网络上，为应用层提供可靠、有序、字节流形式的数据传输服务，适用于对数据完整性要求高、可容忍一定延迟的场景。

#### 一、TCP 的核心特性

1. **面向连接**

   - TCP 通信前必须先建立连接（三次握手），通信结束后需释放连接（四次挥手），通信双方会维护连接的状态信息（如序号、窗口大小等）。
   - 连接是**端到端**的，**仅支持单播通信**，不支持广播或组播。

2. **可靠性**

   TCP 通过一系列机制保证数据可靠传输，核心机制如下：

   - **确认机制**：接收方收到数据后，会向发送方返回**确认报文（ACK）**，发送方只有收到确认才认为数据送达。
   - **重传机制**：若发送方在超时时间内未收到确认，会自动重传数据；同时支持**快速重传**（收到 3 个重复 ACK 时立即重传，无需等待超时）。
   - **序列号与确认号**：每个 TCP 报文段都有唯一序列号，接收方根据序列号对数据排序，避免乱序；确认号则表示期望接收的下一个字节的序号，实现字节级的精准确认。
   - **校验和**：用于检测报文段在传输过程中是否损坏，若校验失败则直接丢弃，触发发送方重传。
   - **超时重传计时器**：发送方为每个已发送未确认的报文段设置计时器，超时则重传。

3. **面向字节流**

   - TCP 将应用层的数据视为连续的字节流，不保留数据的边界（与 UDP 的 “面向数据报” 不同）。
   - 发送方可以分多次发送字节流，接收方也可以分多次接收，TCP 会保证字节的顺序和完整性，应用层可按需读取字节数据。

4. **流量控制**

   - 为避免接收方缓冲区溢出，TCP 通过**滑动窗口机制**实现流量控制。
   - 接收方在报文头中携带**接收窗口大小**，告知发送方当前可接收的字节数；发送方的发送窗口不能超过接收窗口的大小，从而匹配收发双方的处理能力。

5. **拥塞控制**

   - 为避免网络拥塞，TCP 会根据网络状况动态调整发送速率，核心算法包括：
     - **慢启动**：初始阶段指数级增加发送窗口，快速探测网络可用带宽。
     - **拥塞避免**：当达到阈值后，线性增加发送窗口，降低拥塞风险。
     - **快速重传**：快速恢复丢失的报文段，减少重传等待时间。
     - **快速恢复**：拥塞后快速调整窗口大小，恢复传输速率。

6. **头部开销较大**

   - TCP 头部最小为**20 字节**，若包含可选字段则最多可达 60 字节，其核心字段如下：

     | 字段       | 长度   | 说明                                                         |
     | ---------- | ------ | ------------------------------------------------------------ |
     | 源端口号   | 2 字节 | 发送方应用程序端口                                           |
     | 目的端口号 | 2 字节 | 接收方应用程序端口                                           |
     | 序列号     | 4 字节 | 报文段数据的起始字节序号（标记数据部分第一个字节在原始字节流中的位置，可以理解成偏移量） |
     | 确认号     | 4 字节 | 期望接收的下一字节序号（表示序号在该确认号之前的所有字节都已正确收到） |
     | 数据偏移   | 4 位   | 头部长度（单位为 4 字节）                                    |
     | 标志位     | 6 位   | 包含 SYN、ACK、FIN 等控制位                                  |
     | 窗口大小   | 2 字节 | 接收方的可用缓冲区大小                                       |
     | 校验和     | 2 字节 | 校验头部和数据的完整性（TCP 的协议号是 6，UDP 的协议号是 17） |
     | 紧急指针   | 2 字节 | 标记紧急数据的位置                                           |

     * 还有一个保留字段，占6 bit，暂时没用，通常置为全0 （加上表中字段刚好20字节）
     * 标志位介绍：
       * URG：紧急位
         - URG = 1 时，紧急指针有效。表示这是紧急数据，应尽快插队发送
       * ACK：确认位⚡️
         - ACK = 0 时，确认号（ack_seq）无效
         - ACK = 1 时，确认号（ack_seq）有效
         - 只有 **握手 ①** 的 ACK = 0，其他所有 TCP 报文段 ACK = 1
       * PSH：推送位
         - PSH = 1 时，表示希望接收方尽快回复（用于交互式通信）
       * RST：复位位
         - RST = 1 时，表示出现严重差错（如主机崩溃），必须释放连接
         - 也可用于拒绝一个非法报文段（如恶意的黑客攻击）
       * SYN：同步位⚡️
         - SYN = 1 时，表示这是一个连接请求或连接接受报文。
         - 只有 **握手 ①、握手 ②** 的 SYN = 1，其他所有 TCP 报文段都是 SYN = 0
       * FIN：终止位 ⚡️
         - FIN = 1 时，表示此报文段的发送方的数据已发送完毕，要求释放传输连接
         - 只有 **挥手 ①、挥手 ③** 的 FIN = 1，其他所有的 TCP 报文段都是 FIN = 0

#### 二、TCP 的核心流程

##### 1. 连接建立（三次握手）

- **第一次握手**：客户端发送 SYN 报文，请求建立连接，携带初始序列号（ISN）。（起始序号由客户进程自己决定，seq）
- **第二次握手**：服务端收到 SYN 报文后，回复 SYN+ACK 报文，确认客户端的 SYN，同时携带自己的初始序列号。
- **第三次握手**：客户端收到 SYN+ACK 报文后，回复 ACK 报文，确认服务端的 SYN，连接正式建立。

##### 2. 数据传输

- 基于滑动窗口和拥塞控制机制，发送方将**字节流封装成报文段**发送，接收方按序接收并确认，保证数据可靠、有序传输。

##### 3. 连接释放（四次挥手）

- **第一次挥手**：主动关闭方发送 FIN 报文，请求关闭连接。
- **第二次挥手**：被动关闭方回复 ACK 报文，确认 FIN，此时主动关闭方进入半关闭状态（不再发送数据，可接收数据）。
  - 也就是说，这个时候，主动方不能再传输数据，但是被动方的连接还没断，可以继续发送数据
- **第三次挥手**：被动关闭方**数据传输完毕后**，发送 FIN 报文，请求关闭连接。
- **第四次挥手**：主动关闭方回复 ACK 报文，确认 FIN，等待 2MSL（最大报文段生存时间）后，连接彻底释放。

#### 三、TCP 的适用场景

TCP 的可靠性使其适用于对数据完整性要求高的场景：

1. **文件传输**：如 FTP、HTTP/HTTPS 下载，文件不能出现丢失或损坏。
2. **远程登录**：如 SSH、Telnet，指令和反馈的准确性至关重要。
3. **邮件传输**：如 SMTP、POP3，邮件内容需要完整送达。
4. **交易支付**：如电商支付、银行转账，数据不能丢失或重复，否则会导致交易异常。

#### 四、TCP 与 UDP 的核心区别（补充）

| 特性            | TCP                      | UDP                     |
| --------------- | ------------------------ | ----------------------- |
| 连接性          | 面向连接（三次握手）     | 无连接                  |
| 可靠性          | 可靠（确认、重传、排序） | 不可靠（无确认 / 重传） |
| 传输单位        | 字节流                   | 数据报                  |
| 流量 / 拥塞控制 | 支持                     | 不支持                  |
| 头部开销        | 20-60 字节               | 8 字节                  |
| 实时性          | 较低                     | 较高                    |

## HTTP协议

#### HTTP 协议的核心组成

##### 1. 请求（Request）：客户端 → 服务器

请求由 **请求行 + 请求头 + 空行 + 请求体** 四部分组成（GET 请求无请求体）。

```http
# 示例：GET 请求
GET /index.html HTTP/1.1          # 请求行
Host: www.example.com             # 请求头
User-Agent: Mozilla/5.0 (Windows)
Accept: text/html
空行（必须，分隔请求头和请求体）
# 无请求体

# 示例：POST 请求
POST /login HTTP/1.1
Host: www.example.com
Content-Type: application/json
Content-Length: 36

{"username":"test","password":"123456"}  # 请求体
```

- **请求行**：`请求方法 + 请求路径 + 协议版本`

  常见请求方法：

  | 方法    | 用途                     | 幂等性                     |
  | ------- | ------------------------ | -------------------------- |
  | GET     | 获取资源                 | 是（多次请求结果一致）     |
  | POST    | 提交资源（如表单、JSON） | 否（多次提交可能重复创建） |
  | PUT     | 更新资源（全量替换）     | 是                         |
  | PATCH   | 更新资源（部分修改）     | 否                         |
  | DELETE  | 删除资源                 | 是                         |
  | HEAD    | 仅获取响应头（无响应体） | 是                         |
  | OPTIONS | 查看服务器支持的方法     | 是                         |

- **请求头**：键值对，描述请求的附加信息（如 `Host` 指明目标主机，`Content-Type` 指明请求体格式）。

- **请求体**：仅 POST/PUT 等方法有，承载提交的数据（如表单、JSON、文件）。

##### 2. 响应（Response）：服务器 → 客户端

响应由 **状态行 + 响应头 + 空行 + 响应体** 四部分组成。

```http
HTTP/1.1 200 OK                   # 状态行
Server: nginx/1.21.0              # 响应头
Content-Type: text/html; charset=utf-8
Content-Length: 1234
Set-Cookie: session=abc123

<!DOCTYPE html>                   # 响应体
<html>
  <body>Hello World</body>
</html>
```

- **状态行**：`协议版本 + 状态码 + 状态描述`

  状态码分类（共 5 类）：

  | 分类 | 范围    | 含义                 | 示例                                                         |
  | ---- | ------- | -------------------- | ------------------------------------------------------------ |
  | 1xx  | 100-199 | 临时响应，请求已接收 | 100 Continue（继续发送请求体）                               |
  | 2xx  | 200-299 | 成功                 | 200 OK（请求成功）、201 Created（创建资源成功）              |
  | 3xx  | 300-399 | 重定向               | 301 Moved Permanently（永久重定向）、302 Found（临时重定向）、304 Not Modified（资源未修改，使用缓存） |
  | 4xx  | 400-499 | 客户端错误           | 400 Bad Request（请求参数错误）、401 Unauthorized（未授权）、403 Forbidden（禁止访问）、404 Not Found（资源不存在） |
  | 5xx  | 500-599 | 服务器错误           | 500 Internal Server Error（服务器内部错误）、502 Bad Gateway（网关错误）、503 Service Unavailable（服务不可用） |

- **响应头**：键值对，描述响应的附加信息（如 `Content-Type` 指明响应体格式，`Set-Cookie` 向客户端设置 Cookie）。

- **响应体**：服务器返回的实际数据（如 HTML、JSON、图片二进制数据）。

#### 三、HTTP 版本演进

| 版本     | 核心改进                                                     | 发布时间 |
| -------- | ------------------------------------------------------------ | -------- |
| HTTP/1.0 | 基础请求 - 响应模型，短连接                                  | 1996     |
| HTTP/1.1 | 长连接、管道化请求、Host 头、缓存优化                        | 1999     |
| HTTP/2   | 二进制帧、多路复用（一个连接并发处理多个请求）、服务器推送、头部压缩 | 2015     |
| HTTP/3   | 基于 QUIC 协议（UDP 替代 TCP），解决队头阻塞、更快的握手     | 2022     |

#### 四、HTTP 与 HTTPS 的核心区别

| 特性   | HTTP                 | HTTPS                                  |
| ------ | -------------------- | -------------------------------------- |
| 端口   | 80                   | 443                                    |
| 加密   | 明文传输             | TLS/SSL 加密传输                       |
| 安全性 | 低（易被劫持、篡改） | 高（防劫持、防篡改、身份验证）         |
| 性能   | 无加密开销           | 加密 / 解密有少量开销（HTTP/2 可抵消） |
