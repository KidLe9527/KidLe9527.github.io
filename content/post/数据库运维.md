# MySQL高级管理与MyCat分库分表

## 1. MySQL日志

### 1.1 错误日志
- **作用**：记录MySQL服务器启动、停止及运行过程中发生的严重错误信息。
- **特点**：默认开启。
- **默认路径**：`/var/log/mysqld.log`
- **使用场景**：数据库出现故障无法正常使用时，应首先查看此日志。

### 1.2 二进制日志（BINLOG）

#### 1.2.1 介绍
- **记录内容**：所有DDL（数据定义语言）和DML（数据操纵语言）语句，不包括查询语句（SELECT, SHOW）。
- **主要作用**：
    1. 灾难时的数据恢复
    2. MySQL主从复制
- **开启状态**：MySQL 8.0 默认开启。
- **相关参数**：
```

sql

SHOW VARIABLES LIKE '%log_bin%';

```
- `log_bin_basename`：二进制日志文件的基础名前缀。
- `log_bin_index`：二进制日志索引文件，记录当前关联的binlog文件列表。

#### 1.2.2 日志格式
| 日志格式 | 含义                                                                 |
| :------- | :------------------------------------------------------------------- |
| STATEMENT | 基于SQL语句的日志记录，记录对数据进行修改的SQL语句。                   |
| ROW      | 基于行的日志记录，记录每一行数据的变更。（默认格式）                   |
| MIXED    | 混合模式，默认采用STATEMENT，在某些特殊情况下自动切换为ROW格式进行记录。 |
```

sql

SHOW VARIABLES LIKE '%binlog_format%';

```
- **配置方法**：在 `/etc/my.cnf` 中配置 `binlog_format` 参数。

#### 1.2.3 查看二进制日志
- 二进制日志不能直接读取，需使用 `mysqlbinlog` 工具查看。
- **语法示例**：
```

bash

mysqlbinlog [options] log_file

```
#### 1.2.4 删除二进制日志
| 指令                                      | 含义                                                         |
| :---------------------------------------- | :----------------------------------------------------------- |
| `RESET MASTER`                            | 删除全部binlog日志，之后日志编号将从 binlog.000001 重新开始。 |
| `PURGE MASTER LOGS TO 'binlog.*'`         | 删除指定编号之前的所有日志。                                 |
| `PURGE MASTER LOGS BEFORE 'yyyy-mm-dd hh24:mi:ss'` | 删除指定时间之前产生的所有日志。                   |

- **自动删除**：可在配置文件中设置二进制日志的过期时间，到期自动删除。
```

sql

SHOW VARIABLES LIKE '%binlog_expire_logs_seconds%';

```
### 1.3 查询日志
- **记录内容**：记录客户端的所有操作语句（增删改查），而二进制日志不包含查询数据的SQL。
- **默认状态**：未开启。
- **开启配置**：修改 `/etc/my.cnf` 文件
```

ini

\# 开启查询日志，0-关闭，1-开启

general_log=1

\# 设置日志文件名（默认 host_name.log）

general_log_file=mysql_query.log

```
- **注意**：开启后日志文件会记录所有操作，长时间运行可能导致文件非常大。

### 1.4 慢查询日志
- **记录内容**：记录执行时间超过 `long_query_time`（默认10秒）且扫描记录数不小于 `min_examined_row_limit` 的所有SQL语句。
- **默认状态**：未开启。
- **开启配置**：在 `/etc/my.cnf` 中配置
```

ini

\# 开启慢查询日志

slow_query_log=1

\# 设置执行时间参数（单位：秒）

long_query_time=2

\# 记录执行较慢的管理语句

log_slow_admin_statements=1

\# 记录未使用索引的语句

log_queries_not_using_indexes=1

```
- **注意**：配置修改后需重启MySQL服务器生效。

## 2. 主从复制

### 2.1 概述
- **定义**：将主数据库的DDL和DML操作通过二进制日志传到从库，从库重做这些日志，使数据保持同步。
- **拓扑结构**：支持一主多从、链状复制。
- **优点**：
1. 主库故障可快速切换到从库提供服务。
2. 实现读写分离，降低主库访问压力。
3. 可在从库执行备份，避免影响主库服务。

### 2.2 原理
核心：二进制日志（Binlog）
1. **Master**：主库提交事务时，将数据变更记录到Binlog。
2. **Slave**：从库读取主库Binlog，写入中继日志（Relay Log）。
3. **Slave**：从库重做Relay Log中的事件，将变更应用到自身数据。

### 2.3 搭建步骤

#### 2.3.1 准备
- **主库**：192.168.200.200
- **从库**：192.168.200.201
- **基础准备**：两台服务器安装MySQL，完成初始化（设置密码等）。
- **网络**：确保主从库网络互通，开放或关闭防火墙。

#### 2.3.2 主库配置
1. **修改配置文件 `/etc/my.cnf`**
```

ini

\# 服务ID，集群内唯一（1-2^32-1）

server-id=1

\# 是否只读，0-读写，1-只读

read-only=0

\# 忽略同步的数据库（可选）

\# binlog-ignore-db=mysql

\# 指定同步的数据库（可选）

\# binlog-do-db=db01

```
2. **重启MySQL服务**
```

bash

systemctl restart mysqld

```
3. **创建主从复制用户并授权**
```

sql

-- 创建用户（允许任意主机连接）

CREATE USER 'itcast'@'%' IDENTIFIED WITH mysql_native_password BY 'Root@123456';

-- 授予主从复制权限

GRANT REPLICATION SLAVE ON *.*TO 'itcast'@'%';

```
4. **查看二进制日志坐标**
```

sql

SHOW MASTER STATUS;

```
- 记录 `File` 和 `Position` 值，从库配置时需要。

#### 2.3.3 从库配置
1. **修改配置文件 `/etc/my.cnf`**
```

ini

server-id=2  # 唯一，不能与主库相同

read-only=1  # 只读模式

```
2. **重启MySQL服务**
```

bash

systemctl restart mysqld

```
3. **设置主库配置**
- **MySQL 8.0.23+ 语法**：
```

sql

CHANGE REPLICATION SOURCE TO

SOURCE_HOST='192.168.200.200',

SOURCE_USER='itcast',

SOURCE_PASSWORD='Root@123456',

SOURCE_LOG_FILE='binlog.000004',

SOURCE_LOG_POS=663;

```
- **MySQL 8.0.23之前语法**：
```

sql

CHANGE MASTER TO

MASTER_HOST='192.168.200.200',

MASTER_USER='itcast',

MASTER_PASSWORD='Root@123456',

MASTER_LOG_FILE='binlog.000004',

MASTER_LOG_POS=663;

```
4. **开启同步操作**
```

sql

-- 8.0.22之后

START REPLICA;

-- 8.0.22之前

START SLAVE;

```
5. **查看同步状态**
```

sql

-- 8.0.22之后

SHOW REPLICA STATUS;

-- 8.0.22之前

SHOW SLAVE STATUS;

```
#### 2.3.4 测试
在主库执行创建数据库、表、插入数据等操作，观察从库是否同步。

## 3. 分库分表

### 3.1 介绍

#### 3.1.1 问题分析
随着数据量增长，单数据库面临性能瓶颈：
- **I/O瓶颈**：热点数据多，缓存不足导致大量磁盘I/O；请求数据多，带宽不足导致网络I/O瓶颈。
- **CPU瓶颈**：排序、分组、连接查询、聚合统计等SQL耗费大量CPU资源。

**解决方案**：分库分表，将数据分散存储，缓解单一数据库/表的压力。

#### 3.1.2 拆分策略
- **垂直拆分**
- **垂直分库**：根据业务将不同表拆分到不同库。
- **垂直分表**：根据字段属性将不同字段拆分到不同表。
- **水平拆分**
- **水平分库**：将一个库的数据按策略拆分到多个库。
- **水平分表**：将一个表的数据按策略拆分到多个表。

#### 3.1.3 实现技术
- **ShardingJDBC**：基于AOP原理，在应用层对SQL进行拦截、改写、路由。需编码配置，仅支持Java，性能高。
- **MyCat**：数据库中间件，无需修改代码即可实现分库分表，支持多种语言，性能不及ShardingJDBC。

### 3.2 MyCat概述

#### 3.2.1 介绍
- MyCat是开源的、活跃的、基于Java的MySQL数据库中间件。
- 对开发人员透明，连接MyCat即可，底层分库分表策略在MyCat中配置。

#### 3.2.2 下载与安装
- **下载地址**：http://dl.mycat.org.cn/
- **安装环境**：需安装JDK、MyCat。
- **目录结构**：
- `bin`：可执行文件（启动、停止）。
- `conf`：配置文件（schema.xml, rule.xml, server.xml）。
- `lib`：依赖包。
- `logs`：日志文件。

#### 3.2.3 核心概念
- **逻辑库**：MyCat提供的虚拟数据库（如 `DB01`）。
- **逻辑表**：虚拟表，对应分片的实际表。
- **数据节点**：表被分片所在的物理数据库。
- **节点主机**：物理数据库所在的主机。

### 3.3 MyCat入门

#### 3.3.1 需求
对 `tb_order` 表进行数据分片，分为三个数据节点，每个节点位于不同服务器。

#### 3.3.2 环境准备

- **分片服务器**：192.168.200.210, 192.168.200.213, 192.168.200.214

#### 3.3.3 配置

1. **schema.xml** - 配置逻辑库、表、数据节点等
2. **server.xml** - 配置用户及权限
```

#### 3.3.4 测试
- **启动MyCat**：`bin/mycat start`
- **连接MyCat**：
```

### 3.4 MyCat配置详解

#### 3.4.1 schema.xml
- **`<schema>`**：定义逻辑库。
- **`<table>`**：定义逻辑表，配置分片规则。
- **`<dataNode>`**：定义数据节点。
- **`<dataHost>`**：定义物理数据库主机。

#### 3.4.2 rule.xml
- 定义所有拆分表的规则。
- 包含 `tableRule` 和 `function` 标签。

#### 3.4.3 server.xml
- **`<system>`**：系统配置（字符集、端口等）。
- **`<user>`**：用户及权限配置。

### 3.5 MyCat分片实践

#### 3.5.1 垂直拆分（分库）
- **场景**：将商品表、订单表、用户表分到不同数据库服务器。
- **配置**：在 `schema.xml` 中配置不同表指向不同 `dataNode`。
- **全局表**：为解决跨库Join，可将字典表（如省市区表）设置为全局表（`type="global"`），所有节点同步。

#### 3.5.2 水平拆分（分表）
- **场景**：日志表数据量大，按规则分到多个表。
- **配置**：配置逻辑表及水平分片规则。

#### 3.5.3 分片规则
1. **范围分片**：按指定字段范围分配数据。
2. **取模分片**：字段值对节点数取模。
3. **一致性Hash**：解决拓容问题。
4. **枚举分片**：按字段枚举值分片。
5. **应用指定算法**：由应用决定分片。
6. **固定分片Hash**：二进制位操作分片。
7. **字符串Hash解析**：截取子串进行Hash。
8. **按天分片**：按日期周期分片。
9. **自然月分片**：按月分片。

## 4. 读写分离

### 4.1 介绍
- **目的**：将数据库读、写操作分离，主库写，从库读，减轻单库压力。
- **支持**：通过MyCat实现，支持MySQL、Oracle、SQL Server。

### 4.2 一主一从读写分离

#### 4.2.1 原理
基于MySQL主从复制。

#### 4.2.2 配置
- **schema.xml**：配置 `dataHost` 的 `balance` 属性。
- `balance="0"`：不开启读写分离。
- `balance="1"`：全部readHost与备用writeHost参与读负载均衡。
- `balance="2"`：所有读写操作随机分发。
- `balance="3"`：读请求随机分发到writeHost对应的readHost。
- **一主一从建议**：`balance="1"` 或 `balance="3"`。

### 4.3 双主双从读写分离

#### 4.3.1 架构
- **主库**：Master1（写），Master2（备主）
- **从库**：Slave1（读），Slave2（读）
- **互备**：M1与M2互为主备。

#### 4.3.2 配置
- **schema.xml**：配置两个 `writeHost`，互为主备。
- **balance="1"**：所有读请求在 Master2、Slave1、Slave2 间负载均衡。
- **switchType**：设置故障自动切换。

#### 4.3.3 优点
- 高可用：一个主库故障，另一个主库可继续提供写服务。
- 负载均衡：读操作分摊到多个从库。
