## LRU：（Least Recently Used）

* 最近最久未使用页面置换算法

| 版本           | 核心增强点         | 并发性能 | 内存开销 | 适用场景             | 典型业务案例               |
| -------------- | ------------------ | -------- | -------- | -------------------- | -------------------------- |
| 基础 LRU       | 无                 | 低       | 低       | 单线程、无时效性要求 | 配置项缓存                 |
| 固定 TTL LRU   | 统一过期时间       | 低       | 中       | 固定时效场景         | API 结果缓存（5 分钟过期） |
| 差异化 TTL LRU | 自定义过期时间     | 低       | 中       | 时效差异大的场景     | 电商商品缓存               |
| 分片 LRU       | 多分片减少锁竞争   | 高       | 高       | 高并发场景           | 分布式缓存客户端           |
| LRU-K          | 过滤低频访问       | 中       | 中       | 抗缓存污染需求       | 网页缓存、日志查询         |
| 模板化 LRU     | 泛型支持、智能指针 | 中       | 中       | 通用组件、多类型缓存 | 框架级缓存模块             |

LRU-k**核心设计亮点**

1. **抗缓存污染**：通过 k 次访问阈值，过滤 “一次性访问” 的冷数据（如爬虫、临时查询），避免主缓存被无效数据占用。
2. **双队列协同**：
   - 历史队列：按 LRU 淘汰低频访问的计数记录，防止自身膨胀。
   - 主缓存：存储高频数据，按 LRU 淘汰最久未使用的记录。
3. **高效晋升机制**：历史值映射暂存未达标数据的 value，避免因计数未达标而丢失数据，确保晋升时能正确写入主缓存。



KLruKCache的一个潜在问题

> ### 问题核心
>
> `historyValueMap_` 仅在 `historyCount >= k_` 时主动删除，但如果 `accessCountCache_`（记录访问计数的 LRU 缓存）因容量不足**被动淘汰了某个 key**，该 key 对应的 `historyValueMap_` 条目会永远残留，导致内存泄漏。
>
> ### 解决方案：给 `KLruCache` 增加「淘汰回调机制」
>
> 当 `accessCountCache_` 淘汰某个 key 时，触发回调函数，自动清理 `historyValueMap_` 中对应的条目。

| `KLruKCache` 历史映射膨胀 | `historyValueMap_` 仅在 `historyCount>=k_` 时删除，若计数缓存淘汰了 key 但未清理该 map，会导致内存泄漏 | 可给 `accessCountCache_` 加淘汰回调，清理 `historyValueMap_` |

## LFU：（Least Frequently Used）

* 最不经常使用页面置换算法

分类：

- **普通 LFU**：核心规则是 “淘汰访问频率最低的元素；频率相同时淘汰最久未使用（LRU）的元素”，频率值随访问次数无限递增（比如一个元素被访问 1000 次，频率就会到 1000）。
- **限制最大平均访问频数的 LFU**（下文简称 “带阈值 LFU”）：在普通 LFU 基础上，新增 “平均访问频率阈值” 机制 —— 当所有元素的平均访问频率超过设定阈值时，对所有元素的频率值按比例降低（如减半），防止频率值无限增长。



### **内存释放的完整归属关系**

**`class KLfuCache::purge`函数**

| 内存类型               | 分配方式                 | 释放方 / 释放时机                                            | 备注                                                         |
| ---------------------- | ------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 1. `Node` 节点内存     | `std::make_shared<Node>` | `nodeMap_` 清空时，`shared_ptr` 引用计数归 0 → 自动调用 `Node` 析构释放 | `FreqList` 仅管理节点的链表指针，**不持有 Node 内存所有权**（所有权在`shared_ptr`） |
| 2. `FreqList` 对象内存 | `new FreqList(...)`      | `purge()` 中手动 `delete pair.second` → 调用 `FreqList` 析构释放 | `FreqList` 内部的`head_/tail_`（假头 / 假尾节点）由`shared_ptr`自动释放 |
| 3. 哈希表容器自身内存  | 容器默认构造             | 哈希表（`nodeMap_/freqToFreqList_`）析构时（如`KLfuCache`对象销毁）自动释放 | `clear()` 仅清空键值对，**不释放容器本身内存**（容器内存由编译器管理） |

| 操作                      | 释放的内存                   | 未释放的内存（由谁释放）                    |
| ------------------------- | ---------------------------- | ------------------------------------------- |
| `delete pair.second`      | `FreqList` 对象本身          | 无（`FreqList` 内部 Node 由 shared_ptr 管） |

| `nodeMap_.clear()`        | Node 节点（shared_ptr 归 0） | 无                                          |



### 与普通 LFU 的核心区别

| 维度            | 普通 LFU                           | 带阈值 LFU                                                   |
| --------------- | ---------------------------------- | ------------------------------------------------------------ |
| 频率值特性      | 频率值随访问无限递增（无上限）     | 频率值被阈值约束，定期 “重置”（不会无限大）                  |
| 核心数据维护    | 仅维护 “最小频率”，用于淘汰        | 额外维护 “总访问次数、当前平均频率”，触发阈值逻辑            |
| 淘汰逻辑        | 仅基于 “绝对最小频率” 淘汰         | 淘汰逻辑同普通 LFU，但频率值会被动态调整，“最小频率” 会重新计算 |
| 内存 / 计算开销 | 低（仅维护频率→链表映射）          | 高（需遍历所有节点调整频率、重新计算最小频率）               |
| 频率的 “时效性” | 历史访问占比过高（老热点长期占优） | 更关注近期访问（频率重置后，新热点易上位）                   |



### 带阈值 LFU 的特点

> ### 带阈值 LFU 的优势
>
> #### 1. 解决 “频率膨胀” 问题（核心优势）
>
> 普通 LFU 的致命问题是：**早期高频访问的元素（老热点）会占据缓存，即使后续不再访问，其高频率值也会让新热点无法替代**。
>
> #### 2. 频率值可控，减少内存 / 计算开销
>
> * 遍历频率映射表找 “最小频率” 时，遍历范围随频率值扩大而增加。
> * 带阈值 LFU 通过频率重置，将所有元素的频率约束在较小范围（如阈值 = 10，频率值不会远超 10），映射表的键数量可控，遍历 / 查找效率更稳定。
>
> #### 3. 更好的 “热点迁移” 适配性
>
> 在业务场景中，访问热点往往是动态变化的（比如电商大促时，商品 A 是热点；促后商品 B 是热点）。
>
> 普通 LFU 对热点迁移的适配性差（老热点频率太高），而带阈值 LFU 通过频率重置，快速削弱老热点的优势，让新热点能快速成为高频元素，提升缓存命中率。
>
> 
>
> ### 带阈值 LFU 的缺点
>
> #### 1. 额外的性能开销（核心缺点）
>
> - **阈值触发时的全量遍历**：当平均频率超过阈值时，需要遍历所有缓存节点，移除节点→调整频率→重新添加节点→更新最小频率，这个过程是 O (N) 复杂度（N 为缓存容量），违背了普通 LFU“所有操作 O (1)” 的特性，高并发场景下会出现性能尖峰。
> - **统计开销**：需要额外维护 “总访问次数、当前平均频率” 等变量，每次访问（get/put）都要更新这些变量，增加了单次操作的计算量。
>
> #### 2. 阈值设置依赖经验，易 “过调” 或 “欠调”
>
> - 阈值设置过大：等于没生效，依然存在频率膨胀问题；
> - 阈值设置过小：频繁触发频率重置，缓存的 “频率记忆” 失效（比如刚成为热点的元素，频率还没累加就被重置），导致淘汰逻辑混乱，命中率反而下降；
> - 阈值是固定值，无法适配业务访问模式的动态变化（比如高峰 / 低峰期访问频率差异大）。
>
> #### 3. 淘汰逻辑的 “不稳定性”
>
> 频率重置时，所有元素的频率被强制降低，可能导致原本 “低频率但仍有价值” 的元素被误淘汰：
>
> 比如：元素 A 频率 = 5（偶尔访问），元素 B 频率 = 10（老热点），阈值触发后频率减半（A=2，B=5），此时若缓存满，淘汰的仍是 A，但 A 可能是近期仍需访问的元素，而 B 已无访问价值 —— 频率重置打破了 “绝对频率” 的公平性。
>
> #### 4. 实现复杂度提升
>
> 相比普通 LFU，带阈值 LFU 需要额外实现：
>
> - 平均频率计算逻辑；
> - 阈值触发判断；
> - 全量节点频率调整；
> - 频率重置后最小频率的重新计算；
> - 代码复杂度更高，易引入 bug（比如频率重置时的节点链表操作错误、最小频率计算错误）。



### 访问频数修改的时机

带阈值 LFU 的核心变量包括：`curTotalNum_`（总访问频数）、`curAverageNum_`（当前平均访问频数）、`minFreq_`（最小访问频数）、`maxAverageNum_`（最大平均阈值）。以下按**缓存操作类型**拆解各变量的修改时机、计算逻辑和比较逻辑：

| 缓存操作             | 增加 / 减少访问频数                                   | 修改最小访问频数                                         | 计算平均访问频数                                 | 平均频数比较（阈值判断）                                 |
| -------------------- | ----------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------- |
| `get`（命中）        | ✅ 增加：节点频率 + 1 → `curTotalNum_ +=1`             | ✅ 修改：若原频率是`minFreq_`且原链表为空 → `minFreq_++`  | ✅ 计算：`curAverageNum_ = curTotalNum_ / 节点数` | ✅ 比较：`curAverageNum_ > maxAverageNum_` → 触发频率重置 |
| `put`（新增）        | ✅ 增加：新节点频率 = 1 → `curTotalNum_ +=1`           | ✅ 修改：新节点频率 = 1 → `minFreq_ = min(minFreq_, 1)`   | ✅ 计算：`curAverageNum_ = curTotalNum_ / 节点数` | ✅ 比较：`curAverageNum_ > maxAverageNum_` → 触发频率重置 |
| `put`（更新）        | ✅ 复用`get`逻辑 → `curTotalNum_ +=1`                  | ✅ 复用`get`逻辑修改`minFreq_`                            | ✅ 复用`get`逻辑计算平均频数                      | ✅ 复用`get`逻辑比较阈值                                  |
| `kickOut`（淘汰）    | ❌ 减少：淘汰节点频率 = N → `curTotalNum_ -=N`         | ❌ 不直接修改（淘汰后可能触发`updateMinFreq`）            | ✅ 计算：`curAverageNum_ = curTotalNum_ / 节点数` | ❌ 不比较（淘汰不触发阈值逻辑）                           |
| 频率重置（阈值触发） | ✅ 批量修改：所有节点频率降低 → 重新计算`curTotalNum_` | ✅ 强制更新：遍历所有频率链表 → `minFreq_ = 最小非空频率` | ✅ 重新计算：`curAverageNum_ = 新总频数 / 节点数` | ✅ 重置后再次比较（防止仍超阈值）                         |
| `purge`（清空）      | ✅ 清零：`curTotalNum_ = 0`                            | ✅ 重置：`minFreq_ = INT8_`                               |                                                  |                                                          |

* 平均频数比较（阈值判断）---> 这个放到addFreqnum函数就行，只有增加频数才有可能大于阈值～

### 一、命中场景（缓存命中，更新热度 / 调整策略）

1. 命中 LRU_area（原 T1）或 LFU_area（原 T2）
规则：无论命中哪个区域，都将命中项移到 LFU_area 尾部。
逻辑：
命中 LRU_area：说明该项从 “最近使用” 变为 “高频使用”，需提升到频繁命中区；
命中 LFU_area：说明该项仍在高频访问，移到尾部刷新 “热度”（避免被淘汰）；
目的：让高频访问的项长期驻留 LFU_area，提升缓存命中率。



2. 命中 LRU_ghost（原 B1）
规则：
① 增大 p（向 LRU 倾斜，p 是 LRU_area 的目标容量，最大值为cache_capacity）；
② 淘汰 LFU_area 头部项（移到 LFU_ghost）；
③ 将命中的 LRU_ghost 项从幽灵区移除，移到 LFU_area 尾部（重新缓存）。
逻辑：
命中 LRU_ghost 说明 “最近淘汰的 LRU 项仍有访问需求”，需调整策略 —— 扩大 LRU_area 的目标容量，优先保留这类 “近期有用” 的项，同时淘汰 LFU_area 中最久未访问的项腾空间。



3. 命中 LFU_ghost（原 B2）
规则：
① 减小 p（向 LFU 倾斜，p 最小值为 0）；
② 淘汰 LRU_area 头部项（移到 LRU_ghost）；
③ 将命中的 LFU_ghost 项从幽灵区移除，移到 LFU_area 尾部（重新缓存）。
逻辑：
命中 LFU_ghost 说明 “淘汰的高频项仍有访问需求”，需调整策略 —— 缩小 LRU_area 的目标容量，优先保留 LFU_area 的高频项，同时淘汰 LRU_area 中最久未访问的项腾空间。

> #### 1. LRU_area 的容量是否 “小于等于 p”？—— 是 “尽量维持”，允许短暂超界但会快速修正
>
> p 是 LRU_area 的「目标容量」，不是 “硬限制”，但缓存会通过淘汰机制让 LRU_area 尽量贴近 p：
>
> - 正常情况：LRU_area.size () ≤ p（符合目标）；
> - 超界触发修正：当 LRU_area.size ()> p 时（比如未命中场景插入新项后），会**主动淘汰 LRU_area 头部项到 LRU_ghost**，直到 LRU_area.size () ≤ p。
>
> 例：cache_capacity=10，p=6（LRU 目标 6 个位置）。若 LRU_area 现在有 7 个项（超界 1 个），则立即淘汰头部 1 个到 LRU_ghost，让 LRU_area 回到 6 个，符合 p 的目标。
>
> #### 2. 对应的 LFU_area 容量是否 “总容量 - p”？—— 是 “最大可用容量”，实际容量由访问频率决定
>
> 因为总缓存容量上限是 cache_capacity，且 LRU_area 的目标容量是 p，所以 LFU_area 的「最大可用容量」= cache_capacity - p（这是 LFU 能占用的上限）。
>
> 但 LFU_area 的实际容量是动态的：
>
> - 当 LRU_area 刚好达到 p（LRU_area.size ()=p），LFU_area 最多能占 cache_capacity - p 个位置（总容量不超限）；
> - 当 LRU_area 小于 p（比如刚淘汰了 LRU 项），LFU_area 可暂时超过 cache_capacity - p，但一旦后续 LRU_area 新增项达到 p，就会淘汰 LFU_area 头部项（未命中场景 3 的逻辑），让 LFU_area 回到 “总容量 - p” 的上限。
>
> 例：cache_capacity=10，p=6 → LFU 最大可用容量 = 4。若 LRU 现在只有 5 个项（<p=6），LFU 可以暂时有 5 个项（总容量 5+5=10，未超限）；但如果后续 LRU 新增 1 个项达到 6（=p），此时 LRU+LFU=11>10，会淘汰 LFU 头部 1 个项，让 LFU 回到 4 个（符合最大可用容量）。
>
> #### 3. 为什么 p 增大不会导致总容量超限？—— p 是 “目标”，不是 “实际容量”，总容量由 cache_capacity 硬限制
>
> p 仅定义 “LRU 应该有多大”，但实际总容量（LRU_area + LFU_area）始终被 cache_capacity 约束：
>
> - 增大 p 只是 “允许 LRU_area 未来可以占更多位置”，不会改变当前 LRU/LFU 的实际容量；
> - 所有涉及 “插入项” 的操作（比如命中 LRU_ghost 后插入 LFU_area），都必须先 “淘汰 1 个旧项”（比如淘汰 LFU 头部），保证 “一进一出”，总容量不变。
>
> 例：cache_capacity=10，当前 LRU=6、LFU=4（总容量 10），p=6。命中 LRU_ghost 后：
>
> - 增大 p 到 7（允许 LRU 未来最多占 7 个）；
> - 先淘汰 LFU 头部 1 个项（LFU 变为 3，总容量 9）；
> - 再插入 LRU_ghost 命中项到 LFU（LFU 变为 4，总容量 10）；
> - 最终 LRU=6、LFU=4（总容量仍 10），p=7 仅意味着 “后续 LRU 可以新增到 7 个，此时 LFU 会被压缩到 3 个”。



### 二、未命中场景（缓存未命中，插入新项 + 淘汰旧项）

* 核心原则：新项默认插入 LRU_area 尾部（符合 “最近使用” 特性），再根据各区域容量关系淘汰旧项。

场景 1：LRU_area.size() + LRU_ghost.size() < cache_capacity
规则：
① 新项加入 LRU_area 尾部；
② 若 LRU_area.size() > p（LRU_area 超过目标容量），淘汰 LRU_area 头部项到 LRU_ghost。
逻辑：LRU 区 + LRU 幽灵区总容量未超限，可直接插入新项；若 LRU 区超过目标容量，淘汰最久未用的项到幽灵区。

> **幽灵区的 “参考容量”**：`LRU_ghost` 和 `LRU_area` 的总数量，之所以和 cache_capacity 比较，是为了判断 “LRU 体系的候选项是否过多”—— 避免幽灵区记录的淘汰项远超实际缓存容量，导致后续复用逻辑低效（比如幽灵区存了 100 个项，但实际缓存只有 10 个位置，大部分幽灵项复用概率极低）。
>
> cache_capacity 是 “实际存多少项” 的上限，而 “LRU_area + LRU_ghost” 和 cache_capacity 的比较，是 **“幽灵区该存多少候选项” 的参考标准**，两者定义完全不同。
>
> ### 举个具体例子，直观理解
>
> 假设：cache_capacity=10（实际缓存上限 10 项），p=6（LRU_area 目标容量 6 项），当前状态：
>
> - LRU_area.size ()=3（实际缓存的近期项），LFU_area.size ()=4（实际缓存的高频项）→ 实际总缓存 = 3+4=7 < 10（未超限）；
> - LRU_ghost.size ()=2（已淘汰的 LRU 候选项）→ LRU_area + LRU_ghost=3+2=5 < 10（符合场景 1 的前提）。
>
> 此时插入新项，按场景 1 执行：
>
> 1. 新项插入 LRU_area 尾部 → LRU_area.size ()=4（实际总缓存 = 4+4=8 < 10，仍未超限）；
> 2. 检查 LRU_area.size ()=4 是否超过 p=6 → 未超过，所以不淘汰任何项。
>
> 最终结果：实际缓存（4+4=8）仍≤10，LRU_ghost 仍为 2，完全符合 “cache_capacity 是实际缓存上限” 的核心定义。
>
> 如果插入新项后 LRU_area 变成 7（超过 p=6）：
>
> - 则触发规则②，淘汰 LRU_area 头部 1 项到 LRU_ghost → LRU_area.size ()=6（符合 p=6），LRU_ghost.size ()=3；
> - 此时 LRU_area + LRU_ghost=6+3=9 <10，实际缓存 = 6+4=10（刚到 cache_capacity 上限），仍满足所有约束。

场景 2：LRU_area.size() + LRU_ghost.size() ≥ cache_capacity

* （LRU 区 + LRU 幽灵区已满，需先淘汰再插入）
  * --> 说明 “LRU 体系的候选项（实际 + 幽灵）已经够多了”，再插入新项时，不能随便往幽灵区加淘汰项（否则幽灵区会无限膨胀），所以需要先淘汰 LRU_ghost 里最久未被复用的项（

子场景 2.1：LRU_area.size() < cache_capacity
规则：先淘汰 LRU_ghost 头部项，再将新项加入 LRU_area 尾部；
逻辑：LRU 区还有空间，只需淘汰无价值的幽灵项腾位置。

子场景 2.2：LRU_area.size() = cache_capacity
规则：先淘汰 LRU_area 头部项到 LRU_ghost，再将新项加入 LRU_area 尾部；
逻辑：LRU 区已满，需先淘汰最久未用的项到幽灵区，再插入新项。



场景 3：LRU_area.size() + LFU_area.size() > cache_capacity
（实际缓存项总容量超限，需根据 p 淘汰）
规则：
若 LRU_area.size() > p：淘汰 LRU_area 头部项到 LRU_ghost；
若 LRU_area.size() ≤ p：淘汰 LFU_area 头部项到 LFU_ghost；
逻辑：
p 是 LRU_area 的目标容量 —— 若 LRU 区超过目标容量，优先淘汰 LRU 区；若 LRU 区未超目标容量，说明 LFU 区占比过高，淘汰 LFU 区最久未访问的项。



### 总结

* 只要是ARC命中，就会将命中项移到LFU_area队列队尾 （ 对吗？记得问ai确认下）。如果命中的是幽灵队列，就会增加对应队列的目标容量阈值～
* 如果未命中缓存，意味着要插入新项，新项默认插入 LRU_area 尾部（符合 “最近使用” 特性），再根据各区域容量关系淘汰旧项。～





## FIFO 的 Belady异常

> Belady 异常（Belady's Anomaly）是指在使用 **FIFO（先进先出）页面置换算法** 时，当增加缓存（或内存块）的容量后，**缺页率反而升高** 的反常现象。这与大多数缓存算法（如 LRU）中 “容量增大→缺页率降低” 的直觉相悖。
>
> ### 根本原因：
>
> FIFO 算法的置换策略仅基于 **页面进入缓存的顺序**，而非页面的 **访问频率或最近使用情况**。当缓存容量增大时，可能会导致一些 **被频繁访问的页面更早被淘汰**，而一些 **不常访问的页面却被保留更久**，最终导致缺页率上升。
>
> ### 具体解释：
>
> 1. **FIFO 的缺陷**：
>
>    FIFO 维护一个队列，新页面加入队尾，置换时淘汰队头（最早进入的页面）。这种策略完全忽略了页面的访问模式（如某些页面可能在被淘汰后短期内再次被访问）。
>
> 2. **容量增大为何引发异常**：🔥
>
>    当缓存容量增加时，原本会被较早淘汰的 “无用页面” 可能因队列变长而被保留更久，而后续需要频繁访问的页面可能因队列顺序被更早挤出，导致更多的缺页。
>
> 3. **经典示例**：
>
>    假设有页面访问序列 `1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5`：
>
>    - 当缓存容量为 3 时，缺页次数为 9 次；
>    - 当缓存容量增加到 4 时，缺页次数反而增加到 10 次。
>
>    原因是容量增大后，FIFO 保留了更早进入的 “3,4”，而后续频繁访问的 “1,2” 被更早淘汰，导致更多重复缺页。
>
> ### 总结：
>
> Belady 异常的本质是 **FIFO 算法不满足 “栈特性”（Stack Property）**。栈特性指 “对于任何页面访问序列，容量为 n 的缓存中的页面集合一定是容量为 n+1 的缓存中页面集合的子集”。满足栈特性的算法（如 LRU）不会出现 Belady 异常，而 FIFO 不满足，因此可能出现容量增大但缺页率上升的现象。

## 拓展：头文件保护宏

> C/C++ 编译时，`#include "xxx.h"` 本质是把整个头文件的内容 “复制粘贴” 到当前文件中。如果同一个头文件被**多次包含**（比如：A.h 包含 B.h，C.cpp 同时包含 A.h 和 B.h），会导致：
>
> 1. **重复定义错误**：头文件中的结构体、函数声明、全局变量等被重复声明 / 定义（C++ 不允许重复定义）；
> 2. **编译效率降低**：重复处理相同内容，增加编译时间。
>
> ```cpp
> #ifndef KICACHEPOLICY_H  // 1. 检查宏 KICACHEPOLICY_H 是否未定义
> #define KICACHEPOLICY_H  // 2. 如果未定义，定义这个宏（标记“已包含”）
> 
> // 这里是头文件的实际内容（结构体、函数声明、类定义等）
> // ...
> 
> #endif  // 3. 结束条件编译（对应 #ifndef）
> ```
>
> ### 编译过程分析：
>
> - **第一次包含**：`KICACHEPOLICY_H` 未定义 → 执行 `#define KICACHEPOLICY_H` → 编译头文件内容；
> - **后续再次包含**：`KICACHEPOLICY_H` 已被定义 → 跳过 `#ifndef` 和 `#endif` 之间的所有内容（不重复编译）。
>
> ### 关键细节
>
> 1. **宏名必须唯一**：
>    宏名 `KICACHEPOLICY_H` 通常是 “头文件名大写 + 下划线”（比如头文件是 `KiCachePolicy.h` → 宏名 `KICACHEPOLICY_H`），目的是避免和其他头文件的保护宏冲突（如果两个头文件用了相同的宏名，会导致其中一个被错误跳过）。
>
> 2. **等价写法（C++11 及以上）**：
>    部分编译器支持更简洁的 `#pragma once`，效果和头文件保护宏一致：
>
>    ```cpp
>    #pragma once  // 直接声明：该头文件只编译一次
>    // 头文件内容...
>    ```
>
>    但 `#pragma once` 是编译器扩展（不是标准 C++ 语法），兼容性不如 `#ifndef/#define/#endif`（后者支持所有编译器）。
>
> 3. **必须成对出现**：
>    `#ifndef` 必须和 `#endif` 配对，否则会导致编译语法错误（条件编译块未闭合）。
>
> ### 总结
>
> 这两行代码是 C/C++ 头文件的**标准 “防护措施”**，核心目的是：
>
> - 避免头文件重复包含导致的编译错误；
> - 提高编译效率。
>
> 几乎所有正规的 C/C++ 头文件都会包含这类保护逻辑，是工程化开发中的基础规范。



## 辨错：继承的是访问权限，不是内存 🔥

> Q：子类公有继承基类，基类的私有属性其实也继承到子类，但是子类不能直接访问基类的私有属性，必须通过基类的公有方法访问基类的私有属性对吗？事实上子类含有基类的全部属性？
>
> A：
>
> 1. 子类公有继承基类时，**基类的私有属性（private）会被 “继承”**（内存层面存在于子类对象中），但子类**无法直接访问**（语法层面被禁止），必须通过基类提供的「公有 / 保护方法（public/protected）」间接访问；
> 2. 子类**并非必然包含基类的全部属性**—— 仅继承基类的「非静态属性」（静态属性属于类本身，不随对象实例化，本质是 “类级别的共享资源”，而非 “对象属性”）；且基类的私有属性虽在子类对象内存中，但子类无直接操作权。
>
> **子类公有继承基类时，基类的非静态私有属性会继承到子类对象中（内存存在），但子类不能直接访问，必须通过基类的公有 / 保护方法间接访问；子类仅包含基类的全部非静态属性，静态属性不属于子类对象，而是基类级别的共享资源**。



> Q：静态属性有public、protected、private之分吗，静态属性属于类，所有类对象共享一份数据，对吗？那么基类的静态属性，子类可以访问吗？是用基类：：静态属性访问？
>
> A：
>
> 1. 静态属性（`static` 成员变量）**有 public、protected、private 访问权限之分**，权限规则和非静态属性完全一致；
> 2. 静态属性**属于类本身**，不属于任何对象，所有类的实例（对象）共享同一份数据（内存中只有一个副本）；
> 3. 基类的静态属性，子类**能否访问取决于基类的访问权限**，与继承方式（public/protected/private）相关；访问时优先用「类名：：静态属性」（基类名或子类名均可，推荐基类名更清晰），对象也能访问但不推荐。
>
> 总结：静态属性区别于继承属性，可以叠加；区别就是静态属性属于类，不属于对象

### Arc各部分函数流程

* ARC缓存的入口方法
  * put：先检查是否命中👻，动态调整目标容量；然后lru调用put方法默认插入lru缓存，如果key存在lfu缓存中，同样lfu调用put方法更新lfu缓存的值
  * get：先检查是否命中👻，动态调整目标容量；然后先调用lru的get方法，lru的get有第三个参数是shouldTransform，用于判断是否需要转换成lfu
    * 如果get成功，shouldTransform =  true则向lfu中put(key, value)插入缓存（注意：value是引用，这里value是lru调用get方法返回的值）； shouldTransform = false说明不需要转换成lfu； 
    * get失败说明缓存不在lru中，需要调用lfu的get方法，该方法函数签名是bool get (key, value），没有第三个参数



* ArcLfu缓存的方法：
  * put：
    * 如果在Lfu缓存，更新已存在的Lfu缓存节点；（先更新缓存值，再更新缓存频率，也就是从旧频率链表删除，频率+1，加入新频率链表）
    * 如果不存在，插入新节点到Lfu缓存；（如果缓存容量不足，先驱逐一个频率最低的缓存节点，然后将新节点以频率1加入频率哈希和双向链表
      * 注意这里：从主缓存驱逐一个缓存节点，然后需要将这个缓存节点加入幽灵队列，如果幽灵队列容量已满，则先删除一个最久的
  * get：
    * 如果在主缓存，更新缓存节点的频率；如果不在主缓存，直接返回false
  * chechGhost：
    * 检查相应的幽灵缓存的节点哈希
      * 如果存在，则从幽灵缓存的节点哈希和双向链表中删除
      * 如果不存在，直接返回false；



* ArcLru缓存的方法：

  * arcLru的put逻辑：如果命中主缓存，就更新节点的value，并且移除在链表的位置并重新插入最近使用的位置；没有命中主缓存，就加入新节点（如果主缓存容量已满，就驱逐最近最少访问的节点，然后将新节点插入链表和映射）

    * 驱逐的缓存节点会加入幽灵缓存

  * arcLru的get逻辑：如果命中主缓存，将对应值赋值给变量value做返回值，然后通过传入的shouldTransform 检查是否到达转换阈值（首先将节点移动到主链表最近访问，然后增加计数，然后返回计数值大于等于阈值的判断）；如果没有命中主缓存，直接返回false




### Arc幽灵缓存的晋升机制

> ### **幽灵缓存的基本概念**
>
> 幽灵缓存是一种 “影子缓存”，不存储实际数据值，仅保留被主缓存淘汰的键（Key）及其元信息（如访问计数）。它用于追踪近期被淘汰的缓存项，帮助判断这些项是否值得重新加入主缓存，从而优化缓存命中率。
>
> ### **晋升触发条件**
>
> 当访问一个**不在主缓存中**的键时，Arc 会先检查该键是否存在于幽灵缓存中。若存在，则触发幽灵缓存项的晋升，具体场景如下（对应`KArcCache::checkGhostCaches`方法）：
>
> 1. **LRU 幽灵缓存命中**
>
>    若键存在于`ArcLruPart`的幽灵缓存中：
>
>    - 从 LRU 幽灵缓存中移除该键（`lruPart_->checkGhost(key)`）。
>    - 尝试缩减 LFU 主缓存的容量（`lfuPart_->decreaseCapacity()`），并将释放的容量分配给 LRU 主缓存（`lruPart_->increaseCapacity()`）。
>    - 该键重新进入 LRU 主缓存（后续通过`put`或`get`操作添加）。
>
> 2. **LFU 幽灵缓存命中**
>
>    若键存在于`ArcLfuPart`的幽灵缓存中：
>
>    - 从 LFU 幽灵缓存中移除该键（`lfuPart_->checkGhost(key)`）。
>    - 尝试缩减 LRU 主缓存的容量（`lruPart_->decreaseCapacity()`），并将释放的容量分配给 LFU 主缓存（`lfuPart_->increaseCapacity()`）。
>    - 该键重新进入 LFU 主缓存（后续通过`put`或`get`操作添加）。
>
> ### **晋升的核心逻辑**
>
> 1. **容量动态调整**
>
>    幽灵缓存命中后，通过 “牺牲” 另一部分主缓存（LRU 或 LFU）的容量，为当前命中的缓存项腾出空间，实现缓存资源的自适应分配。例如：
>
>    - LRU 幽灵缓存命中时，LFU 主缓存可能会淘汰一个低频项（`ArcLfuPart::evictLeastFrequent`），释放的容量给 LRU 主缓存，让晋升项进入 LRU。
>
> 2. **重新加入主缓存**
>
>    晋升的项会被重新添加到对应的主缓存（LRU 或 LFU）中，并重置其访问计数（如`ArcLruPart::addToGhost`中重置`accessCount_ = 1`），重新参与主缓存的淘汰竞争。
>
> ### **总结**
>
> Arc 的幽灵缓存晋升机制通过以下方式优化缓存策略：
>
> - **追踪价值项**：记录近期被淘汰的项，避免因 “缓存颠簸”（频繁淘汰和重新加入）导致的性能损耗。
> - **动态分配容量**：根据幽灵缓存的命中情况，自动调整 LRU 和 LFU 主缓存的容量比例，优先保留更常访问的项。
> - **平衡访问模式**：结合 LRU（近期访问）和 LFU（频繁访问）的优势，通过幽灵缓存的反馈优化缓存资源分配。
>
> 这种机制使 Arc 缓存能自适应不同的访问模式，在命中率和资源利用率之间取得平衡。

​    

总结：

* ARC缓存包含一个LFU和一个LRU缓存

  * 当调用get或put方法时，首先会检查幽灵缓存，如果命中幽灵缓存，会尝试增加对应缓存的容量减少另一个的容量；

    * 在减少容量时，如果缓存已满，则会驱逐一个满足条件的缓存，给命中的幽灵缓存腾出空间
    * 然后调用对应的get或者put将幽灵缓存重新加入主缓存

    > ### 2. 重新进入的触发时机
    >
    > 键重新进入主缓存的核心触发点是`checkGhostCaches`方法，该方法在`put`和`get`操作前被调用，用于检查键是否存在于任一 Ghost 缓存中，并调整主缓存容量以允许键重新进入。
    >
    > #### （1）通过`put`操作重新进入
    >
    > 当调用`put(key, value)`时：
    >
    > 1. 先执行`checkGhostCaches(key)`，检查键是否在 LRU 或 LFU 的 Ghost 缓存中：
    >    - 若在**LRU 的 Ghost 缓存**中：尝试让 LFU 主缓存减少容量（淘汰其主缓存中的键），若成功，则增加 LRU 主缓存的容量，为当前键腾出空间。
    >    - 若在**LFU 的 Ghost 缓存**中：尝试让 LRU 主缓存减少容量，若成功，则增加 LFU 主缓存的容量，为当前键腾出空间。
    > 2. 无论是否在 Ghost 缓存中，都会执行`lruPart_->put(key, value)`，将键值对添加到**LRU 主缓存**中。
    > 3. 若该键原本存在于**LFU 主缓存**中（`inLfu`为真），则同时执行`lfuPart_->put(key, value)`，更新 LFU 主缓存中的键值对。
    >
    > #### （2）通过`get`操作重新进入
    >
    > 当调用`get(key, value)`时：
    >
    > 1. 同样先执行`checkGhostCaches(key)`，逻辑与`put`时一致，根据 Ghost 缓存中的存在性调整主缓存容量。
    > 2. 优先检查**LRU 主缓存**：
    >    - 若键在 LRU 主缓存中，且满足迁移条件（`shouldTransform`为真，由访问次数等阈值决定），则调用`lfuPart_->put(key, value)`，将键值对添加到**LFU 主缓存**中。
    > 3. 若 LRU 主缓存中不存在，则检查**LFU 主缓存**，若存在则直接返回对应值，键仍保留在 LFU 主缓存中。
    >
    > ### 3. 总结
    >
    > 键重新进入主缓存的本质是：
    >
    > - 当键通过`put`或`get`被再次访问时，若其之前被淘汰并存在于某部分的 Ghost 缓存中，`checkGhostCaches`会调整 LRU 和 LFU 主缓存的容量，为键 "腾出位置"。
    > - 随后通过`lruPart_->put`或`lfuPart_->put`将键值对正式写入对应的主缓存，完成 "重新进入" 的过程。

  * 如果幽灵缓存未命中，则

  > 在 `KArcCache` 中，当 `checkGhostCaches` 检测到未命中幽灵缓存（即返回 `false`）时，下一步逻辑取决于当前操作是 `put` 还是 `get`：
  >
  > 1. **对于 `put` 操作**：
  >    - 直接执行正常的缓存插入逻辑：
  >      - 先向 `lruPart_`（LRU 部分）插入键值对。
  >      - 如果该键原本存在于 `lfuPart_`（LFU 部分），则同时更新 `lfuPart_` 中的值。
  > 2. **对于 `get` 操作**：
  >    - 先尝试从 `lruPart_` 中获取数据：
  >      - 若命中且满足转换条件（`shouldTransform` 为 `true`），则将该键值对同步到 `lfuPart_`。
  >    - 若 `lruPart_` 未命中，则尝试从 `lfuPart_` 中获取数据，命中则返回，未命中则整体缓存未命中。
  >
  > 简言之，未命中幽灵缓存时，缓存会按常规逻辑处理当前的 `put` 或 `get` 操作，不触发 LRU/LFU 部分的容量调整（幽灵缓存命中时才会调整两部分的容量）。
